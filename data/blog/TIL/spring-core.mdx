## ☘️ chap01: 객체 생성과 IoC 컨테이너

프로그램의 객체는 다른 객체와 함께 일한다. 기존 Java 실습은 Application이 new MemberDAO로 직접 객체를 만들고 메서드를 호출했다. Spring은 객체의 생성과 연결을 컨테이너에 맡길 수 있게 한다. **IoC(제어의 역전)**는 이런 생성·연결의 주도권이 사용하는 코드에서 외부 관리 구조로 옮겨간다는 의미다.

컨테이너가 관리하는 객체를 **빈(bean)**이라고 한다. ApplicationContext는 빈을 등록·조회하는 컨테이너의 대표 인터페이스다. 빈을 가져와 메서드를 호출하는 업무 동작과 빈을 만들고 연결하는 설정을 나누어 읽는다.

**세 가지 등록 방식**

XML 방식은 bean에 id와 실제 클래스 이름을 적고 constructor-arg로 생성자 값을 전달한다. GenericXmlApplicationContext가 파일을 읽고 설정대로 객체를 만든다. getBean에 이름과 기대 타입을 주면 해당 객체를 가져온다. 수업은 회원 번호·아이디·비밀번호·이름을 가진 MemberDTO를 등록했다.

Java 설정은 @Configuration 클래스에 @Bean 메서드를 작성한다. 메서드가 반환한 객체가 빈으로 등록되고 AnnotationConfigApplicationContext가 설정 클래스를 읽는다. 이름을 지정하지 않으면 기본적으로 메서드 이름이 빈 이름이다. 원본 section02 실행 파일은 section03의 설정 클래스를 import하고 있어 해당 Java 설정의 member 빈을 사용하려는 의도와 다르다. 같은 이름의 설정 클래스라도 패키지가 맞는지 확인해야 한다.

컴포넌트 스캔은 지정 패키지에서 @Component 등이 붙은 클래스를 찾아 등록한다. 수업은 MemberDAO를 스캔하고 memberDAO라는 이름으로 조회해 기존 회원과 신규 회원을 확인했다. @Controller·@Service·@Repository·@Configuration도 역할에 맞게 사용하는 관련 등록 표식이다. 등록 대상 패키지 밖의 클래스를 자동으로 모두 찾아주는 것은 아니다.

MemberDAO는 DB가 아니라 Map에 회원을 보관한다. 같은 번호를 다시 넣으면 기존 값을 바꾸고 크기는 늘지 않으므로, 크기 증가로 판단하는 insertMember의 성공 결과는 false일 수 있다. 컨테이너 사용과 영구 저장은 다른 문제다.

## ☘️ chap02: 필요한 객체를 전달하는 의존성 주입

의존성은 한 객체가 동작하기 위해 사용하는 다른 객체다. 회원이 계좌의 입출금을 사용한다면 계좌에 의존한다. **의존성 주입(DI)**은 회원 안에서 계좌를 직접 고정 생성하지 않고 바깥에서 필요한 계좌를 전달하는 방식이다. 직접 Java 코드로 전달해도 DI의 형태이며 Spring은 이를 설정과 자동 연결로 관리한다.

수업의 일반 Java 코드는 PersonalAccount를 만든 뒤 회원 setter에 넣는다. XML에서는 실제 구현 클래스로 계좌 빈을 등록하고 member의 property에 ref로 연결한다. value는 숫자·문자 같은 값, ref는 다른 빈 참조라는 차이다. 생성자 주입은 객체가 만들어질 때, setter 주입은 만들어진 뒤 메서드로 필요한 객체를 넣는다.

Java 설정에서는 accountGenerator가 계좌를 만들고 memberGenerator가 이를 회원에 연결한다. 사용하는 쪽은 회원의 personalAccount를 통해 입금 10000·출금 5000·잔액 조회를 수행한다. 계좌를 어디서 만들었는지와 계좌가 실행하는 입출금 규칙은 분리되어 있다.

**계층 구조 예제**

메모 예제는 MemoController → MemoService → MemoRepository 순서다. Controller는 기능 호출의 입구, Service는 처리 흐름, Repository는 데이터 보관과 조회를 맡는다. 실제 구현은 MemoryMemoRepository이며 서비스는 MemoRepository 인터페이스를 생성자로 받는다. 설정 클래스가 어떤 구현을 줄지 정하므로 서비스가 생성 방식을 직접 알 필요가 없다.

설정에서 빈들을 연결하는 시점과 사용자가 메모 조회·등록을 요청해 메서드가 호출되는 시점은 다르다. 이 예제는 역할 분리와 생성자 주입을 함께 이해하는 연습이다.

## ☘️ chap03: 자동 주입과 여러 후보 선택

@Autowired는 컨테이너에서 맞는 타입의 빈을 찾아 연결하게 한다. 필드, setter, 생성자에 적용하는 방식을 비교했다. 필드 주입은 필드에 직접, setter는 변경 메서드로, 생성자는 생성 시 필요한 값을 받는다. 생성자 주입은 의존성을 매개변수에 드러내고 final 필드로 보관할 수 있다. 생성자가 하나뿐이면 수업처럼 @Autowired를 생략할 수 있다.

BookService는 BookDAO를 받아 전체 목록과 한 권 조회를 위임한다. @Service와 @Repository로 등록된 실제 객체가 있어야 주입할 수 있다. 타입만 선언했다고 구현 객체가 저절로 생기는 것은 아니다.

같은 Pokemon 타입의 후보가 여러 개면 무엇을 주입할지 모호할 수 있다. @Primary는 기본으로 우선할 후보를 정하고, @Qualifier는 필요한 빈을 구체적으로 지정한다. 수업에서 기본 후보는 파이리지만 pikachu라는 Qualifier를 명시한 서비스는 피카츄를 받는다. 구체 지정이 기본 우선순위보다 앞선다.

하나를 고르는 대신 `List<Pokemon>`으로 받으면 같은 타입의 여러 빈을 모아 사용할 수 있다. 컬렉션 서비스는 각 포켓몬의 attack을 순회 호출한다. 후보가 여러 개인 문제를 해결하는 것과 모두 필요한 상황을 구분한다.

## ☘️ chap04: 빈 범위와 초기화·설정값

빈의 범위(scope)는 언제 객체를 만들고 같은 것을 재사용할지 정한다. 기본 singleton은 컨테이너의 해당 빈을 다시 조회하면 같은 객체를 돌려준다. 클래스 전체에서 전 세계적으로 하나라는 뜻이 아니라 그 컨테이너의 빈 정의를 기준으로 한다. 여러 사용자가 바꾸는 데이터를 singleton 필드에 보관하면 공유 상태라는 점에 주의한다.

수업의 singleton 장바구니에서 cart1에 붕어빵과 우유를 넣고 cart2로 물을 추가하면 같은 장바구니 내용을 함께 본다. prototype은 요청할 때 새 객체를 만들어 cart2가 별도 목록을 가진다. 다만 새 장바구니라고 그 안에 전달하는 모든 상품 객체까지 자동으로 복제되는 것은 아니다.

@Bean의 initMethod는 객체 생성과 의존성 주입 뒤 준비 작업, destroyMethod는 컨테이너 종료 때 정리할 메서드를 지정한다. Owner의 openShop과 closeShop을 연결하고 context.close로 종료를 확인했다. prototype은 생성 이후의 전체 종료 생명주기까지 singleton처럼 관리된다고 가정하지 않는다.

외부 properties는 @PropertySource로 Spring 환경에 등록하고 @Value로 읽는다. 상품 이름·가격·용량을 필드나 @Bean 매개변수에 주입했다. 파일의 문자열을 대상 int 등으로 변환하므로 값의 형식이 맞아야 한다. 설정을 바깥에 둔 것과 실행 중 파일 수정이 자동 반영되는 것은 별개다.

## ☘️ chap05: 공통 동작을 묶는 AOP

AOP는 여러 업무 메서드에 반복되는 로깅이나 실행 시간 측정 같은 기능을 별도로 모아 적용하는 방식이다. 업무 서비스마다 같은 로그 코드를 넣는 대신 어떤 메서드에 어떤 공통 처리를 실행할지 정의한다. 수업은 @EnableAspectJAutoProxy로 프록시 기반 적용을 켰다. 호출이 프록시를 거쳐 들어올 때 공통 동작과 실제 메서드가 연결된다.

@Aspect 클래스는 적용 조건과 실행할 기능을 모은다. Pointcut은 대상 메서드를 고르는 조건이고 Advice는 그때 실행할 공통 코드다. 수업의 execution 표현식은 지정 패키지에서 이름이 Service로 끝나는 클래스의 메서드들을 고르고 serviceMethods라는 이름으로 재사용한다. `*`는 이름·반환 타입 등에 대한 범위, `(..)`는 여러 매개변수 구성을 뜻한다.

Before는 실행 전, AfterReturning은 정상 반환 후, AfterThrowing은 예외가 밖으로 나간 뒤, After는 정상·예외와 관계없이 종료 시 처리한다. returning·throwing에 적은 이름은 결과나 예외를 받을 Advice 매개변수 이름과 맞춘다. JoinPoint로 메서드 이름과 인수를 읽어 로그를 남긴다.

Around는 실행 전후를 둘러싼다. 수업은 시작 시각을 기록하고 try에서 proceed를 호출한 뒤 finally에서 경과 시간을 계산한다. proceed가 실제 대상 메서드를 진행시키므로 호출하지 않으면 원래 업무가 실행되지 않는다. 결과를 그대로 return하고 예외도 전달하면서 finally로 시간 측정을 끝내야 원래 호출 의미를 보존할 수 있다.
