## ☘️ Next.js의 페이지와 공통 화면

라우팅은 URL에 따라 어떤 화면을 보여 줄지 정하는 일이다. Next.js App Router는 app 아래의 폴더 구조로 경로를 표현한다. 수업의 about/page.js는 소개 페이지, menu/page.js는 메뉴 페이지가 된다. page.js는 그 경로의 내용을 만들고 layout.js는 여러 페이지를 둘러싸는 공통 구조를 만든다.

루트 layout은 html과 body를 포함하고 공통 Layout 컴포넌트에 children을 넘긴다. Layout은 Header·Navbar 다음에 children을 표시하므로 페이지가 바뀌어도 같은 공통 구조 안에서 내용이 바뀐다. dashboard에도 별도 layout을 두면 루트 layout → dashboard layout → dashboard page 순서로 감싼다.

Link는 이동할 주소를 href로 지정하는 컴포넌트다. 페이지 이동에 필요한 코드를 미리 준비하는 프리패칭과 클라이언트 이동을 지원한다. 버튼 처리처럼 코드 실행 뒤 이동해야 할 때는 useRouter의 push를 사용했다. App Router의 관련 Hook은 next/navigation에서 가져온다.

Navbar는 usePathname으로 현재 경로를 읽어 같은 메뉴에 활성 스타일을 붙인다. 이런 클라이언트 Hook을 사용하는 파일에는 `'use client'`를 둔다. pathname에는 검색 조건이 포함되지 않으므로 `/menu?sort=price`에서는 `/menu`다. 원본의 완전 일치 비교는 `/menu/1`까지 메뉴 활성으로 처리하지 않으므로 상세 경로도 포함할지는 별도로 정해야 한다.

## ☘️ 경로 값으로 메뉴 찾기

`menu/[menuCode]/page.js`의 대괄호 폴더는 URL의 그 부분을 값으로 받는 동적 경로다. 메뉴 항목의 Link가 menuCode를 붙인 상세 주소로 이동하고, 상세 페이지는 useParams로 그 값을 읽는다.

```js
export function getMenuByMenuCode(menuCode) {
  return menus.find((menu) => menu.menuCode === Number(menuCode))
}
```

수업의 메뉴는 서버 요청이 아니라 import한 JSON 배열에 있다. URL에서 읽은 코드는 문자열이고 데이터의 menuCode는 숫자이므로 Number로 바꾸어 일치 비교한다. find는 처음 일치하는 객체 하나를 반환하며 없으면 undefined다.

상세 페이지는 처음 menu가 없는 상태로 렌더링되고 Effect에서 menuCode에 맞는 데이터를 저장한다. 그래서 menu?.menuName처럼 아직 값이 없을 때를 고려한다. URL이 바뀌면 다시 조회하도록 Effect의 의존성에 menuCode를 둔다. 실제 데이터의 detail이 없을 수도 있다면 그 중간 단계 역시 안전한지 확인해야 한다.

## ☘️ 검색 조건과 화면 상태 연결

쿼리 문자열은 URL의 물음표 뒤에 붙는 이름과 값이다. 수업의 검색 버튼은 입력한 검색어를 menuName으로 URL에 넣어 검색 페이지로 이동한다. useSearchParams().get으로 값을 읽고 menuName이 바뀔 때마다 Effect에서 결과를 계산한다.

검색 함수는 filter로 각 메뉴를 확인하고 menuName에 검색어가 includes되는 항목들을 새 배열로 반환한다. 경로의 menuCode는 한 대상을 식별하는 값, 검색 문자열의 menuName은 목록을 거르는 조건이라는 차이가 있다.

원본은 검색어를 URL에 바로 이어 붙인다. 특수문자가 들어오면 URL 구조에 영향을 줄 수 있어 인코딩이 필요하며, 검색 키가 없을 때 get이 null이라는 점도 처리해야 한다. 이는 원본의 보완점이며 별도 코드를 수업 구현으로 추가하지 않는다.

검색 내용을 읽는 컴포넌트는 Suspense로 감싸고 fallback 안내를 지정했다. 정적 렌더링에서 useSearchParams를 사용하는 영역의 클라이언트 렌더링 경계를 제공하기 위한 구조다. fallback이 일반적인 Effect 안의 작업 완료를 자동으로 기다려 주는 로딩 상태는 아니다. 개발 서버에서 보이는 결과만으로 프로덕션 빌드 조건까지 같다고 단정하지 않는다.

## ☘️ useReducer로 변경 규칙 모으기

useState는 각 핸들러가 다음 값을 계산해 setter에 전달한다. useReducer는 어떤 변경을 할지 나타내는 action을 dispatch로 보내면 reducer가 현재 상태와 action으로 다음 상태를 계산한다. **이벤트 → dispatch → reducer → 다음 상태 → 화면 반영**이라는 흐름이다.

수업의 reducer는 action.type이 PLUS1이면 1을 더하고 MULTI4이면 4를 곱하며 DIVIDE3이면 3으로 나눈다. 알 수 없는 타입이면 현재 상태를 그대로 반환한다. 초기 0에 세 동작을 순서대로 적용하면 1 → 4 → 4/3이다. 나눗셈에 반올림은 들어 있지 않다.

reducer는 주어진 입력으로 다음 상태를 반환하는 순수한 계산을 담당한다. 핸들러가 계산 방식을 각자 갖는 대신 변경 규칙을 모으므로 처리 종류가 많아질 때 규칙을 살펴보기 쉬워진다. 같은 파일에 useState 버전이 있어 버튼별 setter 계산과 비교할 수 있다. Cart 함수는 비어 있어 장바구니 구현까지 완료된 수업 코드는 아니다.
