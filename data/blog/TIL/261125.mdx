## ☘️ 프롬프트 템플릿

LangChain은 LLM을 쓰는 프로그램에서 프롬프트 작성, 모델 호출, 응답 처리를 연결하는 라이브러리다. 그 첫 부품인 프롬프트 템플릿은 `{변수}` 자리를 비워 둔 프롬프트 틀이다. 문장 구조는 그대로 두고 값만 바꿔 여러 번 쓸 수 있다.

예제는 Python 3.12, `langchain-core` 1.8.4, `langchain-openai` 1.8.5, `pydantic` 2.14.4에서 실행했다. 이 예제는 모델을 호출하지 않으므로 `langchain-core`만 있으면 API 키 없이 실행된다.

```python
# 01_prompt_template.py
from langchain_core.prompts import ChatPromptTemplate, PromptTemplate

def show_prompt_template():
    template = PromptTemplate.from_template("{audience}에게 {topic}에 대해 쉽게 설명하세요.")
    prompt_value = template.invoke({
        "audience": "JAVA를 배운 Python 입문자",
        "topic": "LLM"
    })
    print("문자열 템플릿: ", prompt_value.to_string())

def show_chat_prompt_template():
    template = ChatPromptTemplate.from_messages([
        ("system", "초보자에게 쉬운 말로 설명하세요"),
        ("user", "질문: {question}\n답변 형식: {answer_format}"),
    ])
    prompt_value = template.invoke({
        "question": "LangChain이랑 LangGraph는 어떤 차이가 있어?",
        "answer_format": "표로 시각화해서 보기 쉽게 설명해줘"
    })
    for message in prompt_value.to_messages():
        print(f"[{message.type}]{message.content}")

if __name__ == "__main__":
    show_prompt_template()
    show_chat_prompt_template()
```

```text
문자열 템플릿:  JAVA를 배운 Python 입문자에게 LLM에 대해 쉽게 설명하세요.
[system]초보자에게 쉬운 말로 설명하세요
[human]질문: LangChain이랑 LangGraph는 어떤 차이가 있어?
답변 형식: 표로 시각화해서 보기 쉽게 설명해줘
```

**두 템플릿의 차이**

- `PromptTemplate`: 프롬프트 전체를 하나의 문자열로 만든다. `from_template()`에 넘긴 문장의 `{audience}`, `{topic}`이 변수가 된다.
- `ChatPromptTemplate`: 역할이 붙은 메시지 목록을 만든다. `system` 메시지는 모델의 행동 방식을, `user` 메시지는 실제 요청을 담는다. 채팅 모델은 이렇게 역할이 나뉜 메시지를 입력으로 받는다.

**invoke()의 반환값**

`invoke()`는 변수에 값을 채운 결과를 문자열이 아니라 `PromptValue` 객체로 돌려준다. 이 객체는 `.to_string()`으로 문자열을, `.to_messages()`로 메시지 객체 리스트를 꺼낼 수 있다. 출력에서 `"user"`로 지정한 메시지가 `[human]`으로 나오는 이유는 LangChain이 사용자 메시지를 `HumanMessage`로 바꾸고, 그 `type` 값이 `"human"`이기 때문이다.

템플릿에 있는 변수를 딕셔너리에서 빠뜨리면 `invoke()`가 오류를 낸다. 값이 빠진 프롬프트가 모델로 넘어가지 않게 미리 막아 주는 셈이다.

## ☘️ LCEL로 프롬프트, 모델, 파서 연결하기

LangChain의 템플릿, 모델, 출력 파서는 모두 **Runnable**이다. Runnable은 `invoke(입력)`으로 실행하고 결과를 돌려주는 공통 규칙을 따르는 객체다. 규칙이 같으므로 앞 단계의 출력을 그대로 다음 단계의 입력으로 넘길 수 있다. **LCEL**(LangChain Expression Language)은 이 Runnable들을 `|`로 이어 체인을 만드는 작성 방식이다.

아래 예제는 실제 OpenAI 모델을 호출한다. `langchain-openai`, `python-dotenv` 패키지와 `.env` 파일의 `OPENAI_API_KEY=발급받은_OpenAI_API_키`가 필요하다. `load_dotenv()`가 이 값을 환경변수로 읽고, `ChatOpenAI`는 환경변수에서 키를 찾는다. 원본 코드의 `audience`에는 수강생 이름이 들어 있어 글에서는 이름을 뺐다.

```python
# 02_runnable_chain.py
from dotenv import load_dotenv
from openai import APIError

from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

def build_chain(model):
    prompt = ChatPromptTemplate.from_messages([
        ("system", "LLM 활용을 가르치는 강사입니다. 세 문장 이내로 설명하세요"),
        ("user", "{audience}에게 {topic}을 쉽게 설명하세요")
    ])
    return prompt | model | StrOutputParser()


def main():
    load_dotenv()
    model = ChatOpenAI(
        model="gpt-4.1-mini",
        temperature=0.5,
        max_completion_tokens=200,
        timeout=20,
        max_retries=0,
        use_responses_api=False,
    )
    chain = build_chain(model)
    try:
        result = chain.invoke({
            "audience": "파이썬 입문자",
            "topic": "Langchain에 대한 학습"
        })
    except APIError as error:
        print("요청실패", type(error))
        return
    print("답변:",result)

if __name__ == "__main__":
    main()
```

**체인 안에서 값이 넘어가는 순서**

`chain.invoke({...})`를 호출하면 다음 순서로 실행된다.

1. `prompt`: 딕셔너리로 `{audience}`, `{topic}`을 채워 system·human 메시지가 담긴 `PromptValue`를 만든다.
2. `model`: 메시지를 OpenAI API로 보내고 응답을 `AIMessage` 객체로 받는다. `AIMessage`에는 답변 텍스트(`content`)와 토큰 사용량 같은 부가 정보가 함께 들어 있다.
3. `StrOutputParser()`: `AIMessage`에서 텍스트만 꺼내 `str`로 반환한다.

따라서 `result`는 바로 출력할 수 있는 문자열이다. `|`가 없다면 `prompt.invoke()`, `model.invoke()`, 텍스트 추출을 차례로 직접 호출해야 한다.

**ChatOpenAI 설정**

- `temperature=0.5`: 답의 무작위성 정도다. 0에 가까울수록 같은 입력에 비슷한 답을 낸다.
- `max_completion_tokens=200`: 응답 길이의 상한이다. 넘으면 답이 잘린다.
- `timeout=20`, `max_retries=0`: 20초 안에 응답이 없으면 실패로 처리하고, 실패한 요청을 자동으로 다시 보내지 않는다. 실패는 `openai` 패키지의 `APIError`로 올라오므로 `except APIError`로 처리한다.
- `use_responses_api=False`: OpenAI의 기존 Chat Completions API로 요청한다. `True`면 웹 검색 같은 내장 도구를 쓸 수 있는 Responses API를 쓰고, 지정하지 않으면 LangChain이 사용하는 기능을 보고 고른다.

작성 시점에 실행한 결과다. 모델 응답은 실행할 때마다 달라질 수 있으며, 원본 실행 결과의 이름 호칭은 지웠다.

```text
답변: Langchain은 파이썬으로 만든 도구로, 여러 인공지능 모델을 연결해 복잡한 작업을 쉽게 자동화할 수 있어요. 예를 들어, 텍스트를 이해하고 답변하거나 데이터를 처리하는 과정을 간단하게 만들죠. 파이썬 기본만 알면 Langchain으로 AI 활용을 빠르게 시작할 수 있습니다!
```

## ☘️ 출력 파서로 응답을 검증된 객체로 받기

모델의 응답은 결국 문자열이다. 프로그램에서 감정 분류 결과를 조건문에 쓰려면 문자열을 데이터로 바꾸고, 그 값이 허용된 범위인지도 확인해야 한다. 출력 파서는 이 작업을 체인의 마지막 단계에서 처리한다.

**Pydantic으로 응답 형식 정의하기**

Pydantic은 데이터의 필드와 타입을 클래스로 선언하고, 들어온 값이 그 선언에 맞는지 검사하는 라이브러리다. `BaseModel`을 상속해 필드를 선언하면, 검사를 통과한 값만 객체로 만들어진다.

```python
# 03_output_parser.py
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field
from langchain_core.prompts import PromptTemplate
from langchain_core.output_parsers import JsonOutputParser,PydanticOutputParser
from langchain_core.exceptions import OutputParserException
from langchain_openai import ChatOpenAI
from dotenv import load_dotenv
from openai import APIError

class SentimentAnalysis(BaseModel):
    model_config = ConfigDict(extra="forbid")   # 선언하지 않은 필드가 들어오면 오류
    label: Literal["긍정", "부정", "중립"] = Field(description="허용된 감정 분류")
    reason: str = Field(min_length=1, description="판단 근거")

SAMPLE_REPLY1 = '{"label": "매우 좋음", "reason": "어려움과 긍정적인 평가가 함께 있습니다."}' # label이 긍정,부정,중립이 아닌 예시.
SAMPLE_REPLY2 = '{"label": "중립", "reason": "어려움과 긍정적인 평가가 함께 있습니다."}'
SENTENCE = "수업이 어렵지만 예제가 있어서 따라갈 만하다."

def build_chain(model):
    parser = PydanticOutputParser(pydantic_object=SentimentAnalysis)
    format_instructions = parser.get_format_instructions

    prompt = PromptTemplate.from_template(
        "아래 수강평의 감정을 분류하고 이유를 적으세요.\n"
        "{format_instructions}\n"
        "수강평: {sentence}"
    )

    prompt = prompt.partial(format_instructions=format_instructions)

    return prompt | model | parser

def show_parsers():
    # JsonOutputParser: JSON을 Python 값으로 읽는다.
    format_only = JsonOutputParser()
    data = format_only.invoke(SAMPLE_REPLY1)
    print("JSON 읽기만 한 값: ",data["label"])

    # PydanticOutputParser: JSON을 읽고 SentimentAnalysis 규칙으로 검사한다.
    parser = PydanticOutputParser(pydantic_object=SentimentAnalysis)
    result = parser.invoke(SAMPLE_REPLY2)
    print("결과 타입", type(result).__name__)
    print("감정:",result.label)
    print("이유:",result.reason)

def show_chain():
    load_dotenv()
    model = ChatOpenAI(
        model="gpt-4.1-mini",
        temperature=0,
        max_retries=0,
        timeout=20,
        max_completion_tokens=200,
        use_responses_api=False
    )
    try:
        result = build_chain(model).invoke({"sentence":SENTENCE})
    except OutputParserException:
        print("응답 검증 실패: 감정 분류와 이유 형식을 확인하세요")
        return
    except APIError as error:
        print("API 요청 실패", type(error).__name__)
        return
    print("결과 타입", type(result).__name__)
    print("감정:", result.label)
    print("이유:", result.reason)

if __name__ == "__main__":
    print("\n======== 출력 파서 비교 ========")
    show_parsers()
    print("\n======== 모델 체인 ========")
    show_chain()
```

`SentimentAnalysis`의 규칙은 세 가지다.

- `label`: `Literal["긍정", "부정", "중립"]`이므로 세 값 중 하나만 허용한다.
- `reason`: `min_length=1`이므로 빈 문자열을 허용하지 않는다.
- `extra="forbid"`: 선언하지 않은 필드(예: `"score"`)가 들어오면 오류를 낸다.

`Field(description=...)`의 설명은 검사에는 쓰이지 않고, 뒤에 나오는 형식 안내문에 들어가 모델에게 각 필드의 의미를 알려 준다.

**두 파서의 차이**

`show_parsers()`는 모델 없이 미리 준비한 문자열로 두 파서를 비교한다. 출력 파서도 Runnable이라 `invoke()`에 문자열을 직접 넣을 수 있다.

| 파서                   | 반환값                   | `"label": "매우 좋음"`      |
| ---------------------- | ------------------------ | --------------------------- |
| `JsonOutputParser`     | `dict`                   | JSON 문법만 맞으면 통과한다 |
| `PydanticOutputParser` | `SentimentAnalysis` 객체 | 규칙 위반으로 오류를 낸다   |

`JsonOutputParser`는 JSON을 Python 값으로 바꿀 뿐 내용은 보지 않는다. 그래서 `SAMPLE_REPLY1`의 잘못된 값 `"매우 좋음"`이 그대로 출력된다. `PydanticOutputParser`는 `SAMPLE_REPLY2`처럼 규칙을 지킨 응답만 객체로 만들고, `result.label`처럼 속성으로 값을 읽게 해 준다. `SAMPLE_REPLY1`을 넣으면 `OutputParserException`이 발생한다. 이 동작은 별도로 실행해 확인했다.

**형식 안내문과 partial()**

모델이 규칙에 맞는 JSON을 내려면 형식을 먼저 알아야 한다. `parser.get_format_instructions()`는 `SentimentAnalysis`의 필드와 설명을 JSON 스키마로 정리한 영어 안내문을 만들어 준다. `prompt.partial(format_instructions=...)`은 템플릿 변수 일부를 미리 채운 새 템플릿을 반환한다. 형식 안내문은 매번 같으므로 미리 채워 두고, 실행할 때는 `{"sentence": ...}`만 넘기면 된다.

이 코드는 `get_format_instructions` 뒤에 괄호가 없어 문자열이 아니라 메서드 자체를 넘긴다. 그래도 동작하는 이유는 `partial()`이 인자 없는 함수를 받으면 프롬프트를 만들 때마다 그 함수를 호출해 결과를 넣기 때문이다. 실제로 완성된 프롬프트에 안내문이 들어가는 것을 확인했다. 다만 의도를 분명히 하려면 다음 예제처럼 `get_format_instructions()`로 호출해 문자열을 넘기는 편이 읽기 쉽다.

**실행 결과**

`show_chain()`은 `prompt | model | parser` 체인을 실행한다. 모델 응답이 규칙에 맞지 않으면 `OutputParserException`, API 요청이 실패하면 `APIError`로 처리한다. 작성 시점에 실행한 결과다.

```text

======== 출력 파서 비교 ========
JSON 읽기만 한 값:  매우 좋음
결과 타입 SentimentAnalysis
감정: 중립
이유: 어려움과 긍정적인 평가가 함께 있습니다.

======== 모델 체인 ========
결과 타입 SentimentAnalysis
감정: 중립

```

## ☘️ model_validator로 필드 사이의 규칙 검사하기

`Field`의 조건은 필드 하나만 본다. 객관식 퀴즈에서 "정답은 보기 중 하나여야 한다"는 `answer`와 `choices` 두 필드를 함께 봐야 하는 규칙이라 `Field`만으로는 표현할 수 없다. 이런 규칙은 `@model_validator`로 작성한다.

```python
# 04_quiz_generation.py
import json
from dotenv import load_dotenv
from langchain_core.output_parsers import PydanticOutputParser
from langchain_openai import ChatOpenAI
from openai import APIError
from pydantic import BaseModel, ConfigDict, Field, model_validator
from langchain_core.prompts import PromptTemplate
from langchain_core.exceptions import OutputParserException

SAMPLE_REPLY = json.dumps({
    "question": "Python 딕셔너리에 저장된 값을 찾을 때 사용하는 것은 무엇인가요?",
    "choices": ["키", "리스트의 인덱스", "문자열의 길이", "반복 횟수"],
    "answer": "키",
    "explanation": "딕셔너리는 키와 값을 한 쌍으로 저장하며, 키를 지정해 해당 값을 읽습니다.",
}, ensure_ascii=False)

class Quiz(BaseModel):
    model_config = ConfigDict(extra='forbid')
    question: str = Field(min_length=1, description="퀴즈 문제")
    choices: list[str] = Field(min_length=4, max_length=4, description="보기 네 개")
    answer: str = Field(min_length=1,description="보기 중 정답 문자열")
    explanation: str = Field(min_length=1, description="정답 설명")

    # 각 필드의 검사를 통과한 뒤, 같은 퀴즈의 보기와 정답을 함께 검사한다.
    @model_validator(mode="after")
    def check_answer(self):
        if any(not choice.strip() for choice in self.choices):
            raise ValueError("보기는 비어 있을 수 없습니다.")
        if len(set(self.choices)) != len(self.choices):
            raise ValueError("보기는 서로 달라야 합니다.")
        if self.answer not in self.choices:
            raise ValueError("정답은 보기 중 하나여야 합니다.")
        return self

def build_quiz_chain(model):
    parser = PydanticOutputParser(pydantic_object=Quiz)
    format_instructions = parser.get_format_instructions()
    prompt = PromptTemplate.from_template(
        "{topic} 주제로 입문자용 객관식 퀴즈 하나를 만드세요\n"
        "보기는 내용이 있는 서로 다른 문장 네 개로 작성하세요.\n"
        "정답은 보기 중 하나의 문장을 그대로 적으세요.\n"
        "{format_instructions}"
    )
    prompt = prompt.partial(format_instructions=format_instructions)
    return prompt | model | parser

def show_quiz(model, topic):
    quiz = build_quiz_chain(model).invoke({"topic":topic})
    print("문제:", quiz.question)
    for number, choice in enumerate(quiz.choices, start=1):
        print(f"{number}.{choice}")
    print("정답:", quiz.answer)
    print("해설:", quiz.explanation)

def main():
    load_dotenv()
    model = ChatOpenAI(
        model="gpt-4.1-mini",
        temperature=0.7,
        max_completion_tokens=500,
        timeout=20,
        max_retries=0,
        use_responses_api=False
    )
    try:
        show_quiz(model, "동물")
    except OutputParserException:
        print("퀴즈 검증 실패: 보기와 정답 형식을 확인하세요")
    except APIError as error:
        print("API 요청 실패: ", type(error).__name__)

if __name__ == "__main__":
    main()
```

**검사 순서**

1. 필드 검사: `choices`는 `min_length=4, max_length=4`이므로 보기가 정확히 네 개여야 한다. 리스트에서 `min_length`, `max_length`는 문자열 길이가 아니라 요소 개수다.
2. `mode="after"`인 `check_answer()`: 필드 검사를 통과해 객체가 만들어진 뒤 실행되므로 `self.choices`, `self.answer`를 함께 읽을 수 있다.
   - `choice.strip()`이 빈 문자열이면 공백만 있는 보기다.
   - `set()`은 중복을 없애므로, 길이가 원래 리스트와 다르면 같은 보기가 있다는 뜻이다.
   - `answer`가 `choices` 안에 없으면 정답이 보기와 연결되지 않는다.
3. 규칙을 어기면 `ValueError`를 올린다. `PydanticOutputParser`는 이를 `OutputParserException`으로 바꿔 올리므로, `main()`의 `except OutputParserException`에서 처리된다. 검사를 통과하면 `return self`로 객체를 그대로 돌려준다.

`SAMPLE_REPLY`는 모델 없이 검사를 확인하기 위한 응답이다. `parser.invoke(SAMPLE_REPLY)`는 통과해 `answer`가 `"키"`인 객체를 만들고, `answer`를 보기에 없는 `"값"`으로 바꾸면 `OutputParserException`이 발생한다. 두 경우 모두 별도로 실행해 확인했다.

프롬프트에도 "정답은 보기 중 하나의 문장을 그대로 적으세요"라고 적었지만, 모델이 지시를 항상 지킨다는 보장은 없다. 프롬프트는 규칙을 지킬 가능성을 높이고, 검증 코드는 지키지 않은 응답이 프로그램에 들어오지 못하게 막는다.

`show_quiz()`의 `enumerate(quiz.choices, start=1)`은 보기를 반복하면서 1부터 시작하는 번호를 함께 꺼낸다. 작성 시점에 실행한 결과다. `temperature=0.7`이라 실행할 때마다 다른 퀴즈가 나온다.

```text
문제: 다음 중 고양이에 대한 설명으로 옳은 것은 무엇인가요?
1.고양이는 주로 물고기를 먹는 동물이다.
2.고양이는 밤에도 잘 볼 수 있는 뛰어난 야행성 동물이다.
3.고양이는 하루 종일 물 속에서 생활한다.
4.고양이는 날개가 있어 하늘을 날 수 있다.
정답: 고양이는 밤에도 잘 볼 수 있는 뛰어난 야행성 동물이다.
해설: 고양이는 야행성 동물로, 어두운 환경에서도 잘 볼 수 있는 뛰어난 시력을 가지고 있습니다. 물 속에서 생활하거나 날개가 있어 날 수는 없습니다.
```

## ☘️ RAG와 Document 객체

LLM은 학습한 데이터만 알고 있어 학습센터의 환불 규정처럼 공개되지 않았거나 최근에 바뀐 정보로는 정확히 답하지 못한다. **RAG**(Retrieval-Augmented Generation, 검색 증강 생성)는 질문과 관련된 문서를 먼저 검색하고, 검색한 내용을 프롬프트에 함께 넣어 모델이 그 근거로 답하게 하는 방식이다. 검색하려면 먼저 원본 파일을 프로그램이 다룰 수 있는 형태로 읽어 와야 한다.

LangChain은 읽어 온 문서를 `Document` 객체로 표현한다.

- `page_content`: 검색과 답변에 쓸 본문 텍스트
- `metadata`: 파일명, 페이지 번호 같은 출처 정보를 담는 딕셔너리

본문과 출처를 나누어 두면, 나중에 검색된 문서로 답을 만들 때 "이 답은 `center_policy.txt`에서 왔다"처럼 근거를 함께 보여 줄 수 있다. 사용자는 그 출처로 답이 맞는지 다시 확인할 수 있다.

아래 예제는 예제 파일 옆 `data` 폴더의 TXT 파일 두 개를 읽어 `Document`로 만든다. 읽을 파일은 다음과 같다.

## ☘️ PDF를 페이지별 Document로 만들기

PDF는 페이지로 나뉘어 있다. 페이지마다 `Document`를 하나씩 만들고 페이지 번호를 metadata에 넣으면, 답변의 근거를 "몇 페이지"까지 알려 줄 수 있다. 아래 예제는 `pypdf` 7.1.1의 `PdfReader`로 2페이지짜리 `data/course_handbook.pdf`를 읽는다.

```python
# 02_pdf_documents.py
from pathlib import Path
from langchain_core.documents import Document
from pypdf import PdfReader

DATA_FILE = Path(__file__).resolve().parent / "data" / "course_handbook.pdf"

def main():
    reader = PdfReader(DATA_FILE)
    documents: list[Document] = []

    for page_number, page in enumerate(reader.pages, start=1):
        text = page.extract_text() or "" # 현재 페이지 안의 텍스트를 문자열로 추출
        if not text.strip():
            continue

        document = Document(
            page_content=text.strip(),
            metadata={
                "source": DATA_FILE.name,
                "page": page_number
            }
        )
        documents.append(document)

    print("PDF 전체 페이지 수: ", len(reader.pages))
    print("만들어진 Document 수: ", len(documents))

    for document in documents:
        print(f"\n[{document.metadata} / {document.metadata['page']}페이지]")
        print(document.page_content[:300])

if __name__ == "__main__":
    main()
```

**페이지마다 일어나는 일**

1. `enumerate(reader.pages, start=1)`: 페이지 객체와 1부터 시작하는 번호를 함께 꺼낸다. 사람이 읽는 페이지 번호와 맞추려고 `start=1`을 썼다.
2. `page.extract_text()`: 페이지의 텍스트를 문자열로 추출한다. 텍스트가 없을 때 빈 값이 와도 다음 줄의 `.strip()`에서 오류가 나지 않도록 `or ""`로 빈 문자열을 보장한다.
3. `if not text.strip(): continue`: `strip()`은 앞뒤 공백과 줄바꿈을 지운다. 지운 결과가 빈 문자열이면 빈 페이지이거나 스캔 이미지처럼 추출할 텍스트가 없는 페이지이므로, `Document`를 만들지 않고 다음 페이지로 넘어간다. 내용 없는 문서가 검색 결과에 섞이지 않게 하기 위함이다.
4. 본문과 함께 `source`(파일명), `page`(페이지 번호)를 metadata에 담아 리스트에 추가한다.

이 PDF는 두 페이지 모두 텍스트가 있어 전체 페이지 수와 `Document` 수가 같다. 출력의 `{document.metadata}`는 딕셔너리 전체를 그대로 문자열로 넣은 것이다.


**PDF 텍스트 추출의 한계**

출력에서 보듯 추출한 텍스트에는 PDF의 줄바꿈이 그대로 남아 "오전"과 "수업"처럼 문장 중간이 끊긴다. 1페이지의 출결 표도 칸 구분 없이 "구분", "기준", "정상 출석"이 한 줄씩 나열된다. PDF는 글자를 화면 위치에 배치하는 형식이라, 문단이나 표 구조가 텍스트로 그대로 옮겨지지 않는다. RAG에서 PDF를 쓸 때는 추출 결과를 직접 확인해 보는 것이 좋다.
