# 🍀 Zustand와 서버 데이터 관리

오늘은 같은 카운터를 여러 컴포넌트에서 사용하는 예제로 Props Drilling과 Zustand를 비교했다. 이후 사용자·장바구니·UI 상태를 나누고, 테마 저장, 비동기 요청, TanStack Query, 게시글 CRUD까지 연결해 봤다.

## Props Drilling과 Zustand의 기본 구조

**중간 컴포넌트가 사용하지 않는 props까지 전달하게 되는 상황**

처음에는 `page → Child → GrandChild` 순서로 `count`와 `setCount`를 전달했다. `Child`는 카운터를 직접 사용하지 않지만, `GrandChild`가 필요로 하므로 두 값을 계속 내려줘야 한다. 이런 전달 단계가 길어지는 것이 Props Drilling이다.

Zustand에서는 상태를 컴포넌트 밖의 store에 두고 필요한 컴포넌트가 같은 store를 읽는다. 실습에서는 `page`, `Parent`, `GrandChild`가 카운터를 공유했고, 중간 `Child`는 props를 전달할 필요가 없어졌다.

**상태와 상태를 바꾸는 액션을 함께 정의하기**

```js
import { create } from 'zustand'

export const useStore = create((set) => ({
  count: 0,
  text: '',
  increase: () => set((state) => ({ count: state.count + 1 })),
  decrease: () => set((state) => ({ count: state.count - 1 })),
  setText: (value) => set({ text: value }),
}))
```

`create()`로 만든 `useStore`는 컴포넌트에서 사용할 수 있는 훅이다. `count`, `text`는 데이터이고, `increase`, `setText`는 데이터를 변경하는 방법이다.

`set()`은 기본적으로 최상위 상태를 얕게 병합한다. 따라서 `set({ text: value })`로 문자열만 바꿔도 카운터와 액션은 유지된다. 기존 값으로 다음 값을 계산할 때는 `set((state) => ...)`를 사용한다.

실습에서는 `const { count, increase } = useStore()`처럼 전체 store를 구독했다. 필요한 값만 선택하는 형태로 정리하면 다음과 같다.

```jsx
'use client'

import { useStore } from '@/store/useStore'

export default function Counter() {
  const count = useStore((state) => state.count)
  const increase = useStore((state) => state.increase)

  return <button onClick={increase}>count: {count}</button>
}
```

위 코드는 실습을 정리한 예시다. `count`만 선택하면 관련 없는 `text` 변경으로 이 구독값이 바뀌지는 않는다. 원본의 `'usec client'`는 지시문 오타이므로 독립적인 Client Component 경계를 선언할 때는 정확히 `'use client'`라고 적어야 한다.

## 역할별 store와 새로고침 이후의 상태

**사용자·장바구니·UI를 나누기**

심화 실습에서는 `useUserStore`, `useCartStore`, `useUIStore`로 관심사를 나눴다. 사용자 정보, 상품 목록, 모달·사이드바 열림 여부를 각각 관리하니 어떤 상태를 어디에서 변경하는지 찾기 쉬워졌다.

장바구니처럼 배열을 다룰 때는 기존 배열을 직접 수정하지 않고 새 배열을 만든다. 추가는 전개 문법, 삭제는 `filter()`를 사용했다. 원본 삭제 액션에는 중괄호를 쓴 콜백에서 `return`이 빠져 있었다. 모든 항목이 `undefined`를 반환하면 `filter()` 결과는 빈 배열이 되므로 아래처럼 정리해야 한다.

```js
addItem: (item) =>
  set((state) => ({ items: [...state.items, item] })),

removeItem: (id) =>
  set((state) => ({ items: state.items.filter((item) => item.id !== id) })),

clearCart: () => set({ items: [] }),
```

이는 store 내부 액션을 발췌해 수정한 예시다. 화살표 함수의 `() => 표현식`은 바로 반환하지만, `() => { ... }`에는 명시적인 `return`이 필요하다.

**persist로 테마 저장하기**

일반 store의 메모리 상태는 페이지를 새로고침하면 초기화된다. 테마처럼 다시 접속해도 유지하고 싶은 값은 `persist` 미들웨어로 저장할 수 있다.

```js
import { create } from 'zustand'
import { persist } from 'zustand/middleware'

export const usePersistStore = create(
  persist(
    (set) => ({
      theme: 'light',
      toggleTheme: () => set((state) => ({ theme: state.theme === 'light' ? 'dark' : 'light' })),
    }),
    { name: 'theme-storage' }
  )
)
```

기본 저장소는 브라우저의 `localStorage`이고, `name`은 저장할 때 사용하는 키다. 여기서는 `theme-storage` 아래에 테마 상태를 보관한다.

Next.js에서는 서버가 브라우저 저장소의 값을 알 수 없어서 서버 출력과 브라우저의 첫 화면이 달라질 수 있다. 실습은 `isMounted`의 초기값을 `false`로 두고, `useEffect`에서 `true`로 바꾼 뒤 테마 화면을 표시했다. 처음에는 양쪽 모두 같은 로딩 화면을 보여주는 방식이다.

이때 **컴포넌트 마운트와 저장된 상태의 복원 완료는 다른 개념**이다. 실습의 마운트 확인은 브라우저 테마 표시를 늦추는 방법이며, 비동기 저장소까지 사용하는 경우에는 별도로 복원 완료 여부를 확인해야 한다.

## 비동기 액션, TanStack Query와 CRUD

**Zustand 액션 안에서 API 요청하기**

`useUserStore`의 `fetchUser()`는 요청 전에 `loading`을 켜고, 응답을 `user`에 저장한 뒤 `finally`에서 로딩을 해제했다. 페이지에서는 `useEffect`에서 이 액션을 호출하고, 로딩 중인지와 사용자 데이터가 있는지에 따라 화면을 나눴다.

비동기 함수도 필요한 시점에 `set()`을 호출하면 store 상태를 변경할 수 있다. 다만 원본은 HTTP 성공 여부를 확인하지 않고 실패를 콘솔에만 남겼다. 다시 작성할 때는 `response.ok` 확인과 화면에 표시할 에러 상태까지 함께 관리해야 한다. 또한 홈 화면에서 호출하는 `login`, `logout`은 최종 store에서 주석 처리되어 있어 액션 이름과 호출부가 맞는지도 확인할 필요가 있다.

**서버에서 가져온 목록을 Query로 관리하기**

TanStack Query 실습에서는 `Providers`에서 `QueryClientProvider`를 적용하고, `useState(() => new QueryClient())`로 클라이언트를 유지했다. 렌더링마다 새 객체를 만들지 않아 같은 컴포넌트 인스턴스가 사용하는 캐시를 유지할 수 있다.

사용자 목록 요청은 다음처럼 작성했다.

```jsx
const { data, isLoading, isError, error, refetch, isFetching } = useQuery({
  queryKey: ['users'],
  queryFn: fetchUsers,
})
```

- `queryKey`는 데이터를 캐시에서 구분하는 키다. 사용자 목록과 특정 사용자 상세는 서로 다른 키로 구분할 수 있다.
- `queryFn`에는 데이터를 반환하거나 실패 시 에러를 던지는 비동기 함수를 전달한다.
- 이 실습의 `isLoading`은 데이터가 없는 최초 요청의 로딩 화면에 사용했다.
- `isFetching`은 데이터를 이미 보여주고 있어도 다시 요청 중이면 켜지므로, 목록 위에 갱신 안내를 표시할 수 있다.
- `refetch()`로 같은 쿼리를 다시 요청할 수 있다.

Zustand에서는 사용자 정보·장바구니·모달 상태를 관리했고, Query에서는 API 데이터의 요청 상태와 캐시를 관리했다. 서버 데이터를 Zustand에 저장하는 것도 가능하지만, Query를 사용하면 요청·캐시 관리 기능을 활용할 수 있다.

**게시글 CRUD와 API 함수 분리**

`json-server`로 `db.json`을 제공하고, `postAPI` 객체에 통신 코드를 모았다. 화면은 API 함수 호출과 상태 변경에 집중했다.

| 작업       | HTTP 메서드 | 요청 경로         |
| ---------- | ----------- | ----------------- |
| 목록 조회  | GET         | `/posts`          |
| 새 글 등록 | POST        | `/posts`          |
| 제목 수정  | PATCH       | `/posts/게시글ID` |
| 글 삭제    | DELETE      | `/posts/게시글ID` |

등록·수정 요청에서는 `Content-Type: application/json`과 `JSON.stringify()`로 본문을 전달했다. 각 함수가 `response.ok`를 확인하고 실패 시 에러를 던지므로, 화면에서는 `try-catch`로 처리할 수 있다.

이 CRUD 페이지는 `useState`로 목록·로딩·에러를 직접 관리했고, 등록·수정·삭제가 끝나면 `loadPosts()`를 다시 호출해 서버의 목록을 화면에 반영했다. 같은 날 작성한 Query 페이지와는 별도 예제이며, 아직 mutation으로 연결한 구조는 아니다.

오늘 기억할 부분은 **상태를 공유하는 위치, 새 배열로 갱신하는 방법, 저장소에 남길 값, 서버 요청 상태를 관리할 도구를 각각 판단하는 것**이다. store를 만든 뒤에도 액션의 반환값, 호출부와의 이름 일치, 로딩 종료 처리를 놓치지 않아야 한다.
