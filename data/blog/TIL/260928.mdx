## ☘️ 공유 상태와 Zustand store

서로 떨어진 컴포넌트가 같은 값을 써야 할 때 부모가 state를 갖고 props로 전달할 수 있다. 하지만 중간 컴포넌트가 직접 쓰지도 않는 값을 계속 전달하면 연결 단계가 길어진다. 이를 Props Drilling이라고 한다. 수업은 page → Child → GrandChild로 count와 setter를 전달하는 구조를 외부 store를 사용하는 구조와 비교했다.

Zustand의 store는 여러 컴포넌트가 함께 사용할 상태와 상태 변경 함수를 보관하는 공간이다. create로 상태를 읽을 Hook을 만들고 필요한 컴포넌트가 그 Hook을 사용한다.

```js
export const useStore = create((set) => ({
  count: 0,
  text: '',
  increase: () => set((state) => ({ count: state.count + 1 })),
  decrease: () => set((state) => ({ count: state.count - 1 })),
  setText: (value) => set({ text: value }),
}))
```

count와 text는 데이터이고 increase 등은 변경 동작인 액션이다. set은 전달한 최상위 항목을 기존 상태와 얕게 합친다. text만 바꿔도 count와 다른 액션이 지워지지 않는다. 이전 값으로 계산할 때는 현재 state를 받는 함수를 전달한다. 필요한 값만 선택해 구독하면 관련 없는 변경에 대한 반응을 줄일 수 있다.

상태가 바뀌면 그 상태를 구독한 화면도 새 값을 표시한다. 중간 Child가 count를 다시 전달할 필요가 없다. 원본 GrandChild의 `'usec client'`는 `'use client'` 오타이며 유효한 클라이언트 지시문이 아니다.

## ☘️ 관심사별 store와 저장 상태 복원

고급 실습은 사용자, 장바구니, 모달·사이드바 상태를 별도 store로 나눴다. 각각 어떤 데이터를 관리하고 어떤 액션을 제공하는지 한곳에서 확인할 수 있다. 장바구니 추가는 기존 배열을 펼친 새 배열, 전체 삭제는 빈 배열을 전달한다.

개별 삭제의 원본 filter는 중괄호 안에서 비교만 하고 return하지 않는다. filter는 반환값이 참인 항목만 남기므로 이 코드는 모든 항목을 제거한다. 비교 결과를 반환해야 지정 id만 제외할 수 있다. 사용자 화면은 login·logout을 호출하지만 store의 두 구현은 주석 처리되어 있어 이름만 맞춘 것으로는 동작하지 않는다.

**영속화(persist)**

메모리에만 둔 상태는 새로고침으로 앱이 다시 시작되면 초기화된다. persist는 테마 상태를 브라우저 저장소에 저장하고 다시 읽는 데 사용한다. 수업의 theme-storage는 localStorage에서 구분하는 이름이고 테마는 light와 dark 사이를 전환한다.

서버에는 브라우저의 localStorage가 없으므로 처음 만든 화면과 브라우저가 복원한 화면이 다를 수 있다. 이 차이는 hydration, 즉 서버가 만든 화면에 브라우저 동작을 연결하는 단계에서 문제가 된다. 실습은 첫 렌더링에는 같은 로딩 화면을 보여 주고 마운트 Effect 후 테마를 표시한다. 마운트가 끝난 것과 비동기 저장소의 복원이 끝난 것은 별개의 상태다.

## ☘️ 비동기 액션과 TanStack Query

사용자 요청 액션은 loading을 true로 설정 → fetch 요청 → JSON 읽기 → user 저장 → finally에서 loading을 false로 바꾸는 순서다. 화면은 Effect에서 액션을 호출하고 로딩 여부와 user 유무를 표시한다. 원본은 HTTP 성공 여부 검사와 오류 state가 없어 네트워크 실패가 콘솔에만 남는 부분이 있다.

TanStack Query는 서버 데이터 요청의 결과와 진행 상태, 캐시를 관리한다. 캐시는 이전 결과를 보관해 다시 사용하는 저장 공간이다. QueryClient는 그 데이터를 관리하고 QueryClientProvider는 하위 컴포넌트에 공급한다. 수업은 useState의 초기화 함수로 QueryClient를 한 번 마련해 렌더링마다 새 객체를 만들지 않게 했다.

useQuery에 queryKey와 queryFn을 전달한다. queryKey는 어떤 데이터를 보관하는지 구분하는 이름이고 queryFn은 데이터를 반환하거나 실패를 던지는 함수다. 목록과 특정 사용자는 서로 다른 키로 구분해야 한다. isLoading으로 최초 로딩을 표시하고, 기존 데이터가 있더라도 요청 중이면 isFetching으로 최신 데이터 확인을 표시한다. isError와 error로 실패를 보여 주고 refetch로 같은 요청을 다시 실행한다.

## ☘️ 게시글 CRUD의 요청 흐름

CRUD는 생성·조회·수정·삭제다. 수업의 게시글 실습은 json-server의 posts를 대상으로 postAPI에 통신을 모으고 화면은 useState로 관리한다. 이 예제는 Query의 mutation에 연결된 구조가 아니다.

조회는 GET, 등록은 POST, 일부 수정은 PATCH, 삭제는 DELETE를 사용한다. 등록·수정은 Content-Type을 application/json으로 지정하고 JSON.stringify로 객체를 요청 본문 문자열로 만든다. 각 API 함수는 response.ok가 아니면 오류를 던져 화면의 catch가 처리하게 한다.

목록 로딩은 loading 시작과 이전 오류 초기화 → getPosts → posts 저장 → 성공·실패 뒤 loading 종료 순서다. 등록·수정·삭제 성공 후 loadPosts를 다시 호출하므로 서버에 반영된 최신 목록을 화면에 보여 준다. 삭제는 사용자 확인 후 실행한다. 원본 삭제 실패 문구는 “게시글 수정 실패”로 되어 있어 실제 작업과 안내가 맞지 않는 보완점이 있다.
