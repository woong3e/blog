주문과 주문 항목처럼 함께 만들어지고 함께 사라지는 엔티티는 저장과 삭제를 한 곳에서 관리하는 편이 안전하다. 그리고 `@Transactional`을 붙였다고 해서 모든 예외에서 롤백되는 것은 아니다. 이 글은 `cascade`와 `orphanRemoval`로 부모·자식의 생명주기를 묶는 방법, 예외 종류와 호출 방식에 따라 달라지는 트랜잭션의 커밋과 롤백, 생성·수정 시각을 자동으로 기록하는 JPA Auditing을 주문 예제와 테스트로 확인한다. 로컬 MySQL의 `menudb`에서 테스트 8개를 실행해 모두 통과했다.

## ☘️ 준비: 테이블과 설정

기존 `tbl_menu`, `tbl_category`는 그대로 두고 주문용 테이블 두 개를 추가한다. 아래 스크립트를 먼저 실행해야 한다. 주문 항목(`practice_order_line`)이 외래 키로 주문(`practice_order`)을 참조한다.

## ☘️ cascade와 고아 객체 삭제

**연관관계와 생명주기**

주문(`PurchaseOrder`)은 여러 주문 항목(`OrderLine`)을 가지는 1:N 관계다. 외래 키는 항목 테이블에 있으므로 연관관계의 주인은 `OrderLine.order`이고, 주문 쪽 컬렉션에는 `mappedBy = "order"`를 적는다. 이 관계에서 항목은 주문 없이는 의미가 없으므로 주문의 생명주기에 맡긴다.

- `cascade = CascadeType.PERSIST`: 부모를 저장(`persist`)할 때 컬렉션 안의 자식도 함께 저장한다. 주문을 저장하면 항목을 따로 저장하지 않아도 된다.
- `orphanRemoval = true`: 부모의 컬렉션에서 빠진 자식을 고아 객체로 보고 삭제한다. 부모를 삭제하면 소유하던 자식도 함께 삭제된다.

주의할 점은 `cascade`가 `PERSIST`만 지정되어 있다는 것이다. 삭제 전파는 `cascade`가 아니라 `orphanRemoval = true`가 맡고 있고, 아래 테스트가 이를 확인한다.

`PurchaseOrder.removeLine`은 컬렉션에서 항목을 빼고(`lines.remove`) 항목의 `order` 참조도 끊는다(`assignOrder(null)`). 컬렉션과 참조 중 한쪽만 바꾸면 메모리의 객체 그래프가 어긋나기 때문이다. `OrderLine.assignOrder`는 같은 패키지에서만 호출할 수 있게(package-private) 두었으므로, 다른 패키지에서는 `PurchaseOrder`의 메서드를 거쳐야 양쪽 참조가 함께 바뀐다.

**`src/main/java/com/ohgiraffers/practicaljpa/order/PurchaseOrder.java`**

```java
package com.ohgiraffers.practicaljpa.order;

import com.ohgiraffers.practicaljpa.common.BaseTimeEntity;
import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.List;

@Entity
@Table(name = "practice_order")
public class PurchaseOrder extends BaseTimeEntity {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Column(nullable = false)
    private String customer;
    // 부모 저장 전파와 고아 객체 삭제를 설정한다.
    // orphanRemoval = true : 관리중인 부모에서 빠진 자식 삭제, 부모 삭제하면 자식들도 삭제
    @OneToMany(mappedBy = "order", cascade = CascadeType.PERSIST,
    orphanRemoval = true)
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {}

    public PurchaseOrder(String customer) { this.customer = customer; }

    public void addLine(OrderLine line) {
        lines.add(line);
        line.assignOrder(this);
    }
    public void removeLine(Long lineId) {
        OrderLine line = lines.stream().filter(item -> item.getId().equals(lineId))
                .findFirst().orElseThrow(() -> new java.util.NoSuchElementException("주문항목 없음"));
        lines.remove(line);
        line.assignOrder(null); // 메모리의 자식 참조도 끊는다
    }
    public void changeCustomer(String customer) {
        this.customer = customer;
    }

    public Long getId() { return id; }
    public String getCustomer() { return customer; }
    public List<OrderLine> getLines() { return lines; }
}
```

**`src/main/java/com/ohgiraffers/practicaljpa/order/OrderLine.java`**

```java
package com.ohgiraffers.practicaljpa.order;

import jakarta.persistence.*;

@Entity
@Table(name = "practice_order_line")
public class OrderLine {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id", nullable = false)
    private PurchaseOrder order;

    @Column(nullable = false)
    private String menuName;
    private int quantity;

    protected OrderLine() {}

    public OrderLine(String menuName, int quantity) {
        if (quantity < 1) throw new IllegalArgumentException("수량은 1 이상이어야 합니다.");
        this.menuName = menuName;
        this.quantity = quantity;
    }

    void assignOrder(PurchaseOrder order) {
        this.order = order;
    }

    public Long getId() { return id; }
    public String getMenuName() { return menuName; }
    public int getQuantity() { return quantity; }
}
```

**서비스**

`OrderService`는 응답용 `record`(값을 담는 클래스를 짧게 선언하는 Java 문법)를 안에 선언하고, 주문 생성·조회·항목 삭제·고객 이름 변경·삭제를 제공한다. `create`는 항목 두 개를 가진 주문을 만들어 `saveAndFlush`로 저장한다. 아래 서비스에는 다음 절에서 쓰는 롤백 실험용 메서드(`failRuntime` 등)도 함께 들어 있다.

**`src/main/java/com/ohgiraffers/practicaljpa/order/OrderService.java`**

```java
package com.ohgiraffers.practicaljpa.order;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.io.IOException;
import java.time.LocalDateTime;
import java.util.List;
import java.util.NoSuchElementException;

@Service
public class OrderService {

    private final OrderRepository orders;
    public OrderService(OrderRepository orders) { this.orders = orders; }

    // record: 데이터를 전달할 클래스를 간단히 선언하는 문법
    // 각 값을 보관하는 private final 필드와, 순서대로 값을 받는 생성자, 각 값을 읽는 메소드를 제공
    public record LineResponse(Long id, String menuName, int quantity) {}

    public record OrderResponse(Long id, String customer, List<LineResponse> lines,
                                LocalDateTime createdAt, LocalDateTime updatedAt) {}

    // 엔티티 값을 읽어 위의 응답 객체들로 만드는 메서드
    private OrderResponse toResponse(PurchaseOrder order) {
        return new OrderResponse(order.getId(), order.getCustomer(),
                order.getLines().stream()
                        .map(line -> new LineResponse(line.getId(), line.getMenuName(), line.getQuantity()))
                        .toList(), order.getCreatedAt(), order.getUpdatedAt());
    }

    @Transactional
    public OrderResponse create(String customer) {
       PurchaseOrder order = new PurchaseOrder(customer);
       order.addLine(new OrderLine("아메리카노", 2));
       order.addLine(new OrderLine("카페라떼", 1));
       orders.saveAndFlush(order);

        return toResponse(order);
    }

    @Transactional
    public void failRuntime(String customer) {
        orders.saveAndFlush(new PurchaseOrder(customer));
        throw new IllegalStateException("저장 후 실패");
    }

    @Transactional
    public void failCheckedDefault(String customer) throws IOException {
        orders.saveAndFlush(new PurchaseOrder(customer));
        throw new IOException("체크 예외 기본 규칙 확인");
    }

    @Transactional(rollbackFor = IOException.class)
    public void failCheckedRollback(String customer) throws IOException {
        orders.saveAndFlush(new PurchaseOrder(customer));
        throw new IOException("체크 예외도 롤백");
    }

    @Transactional
    public void swallowFailure(String customer) {
        try{
            orders.saveAndFlush(new PurchaseOrder(customer));
            throw new IllegalStateException("업무 단계 실패");
        } catch (IllegalStateException e) {
            // 프록시 밖으로 전달되지 않는다 -> 결국 프록시는 정상 반환을 보므로 커밋한다.
        }

    }

    // 같은 객체 안에서 호출하므로 failRuntime()의 @Transactional을 거치지 않는다.
    public void selfInvocation(String customer) {
        failRuntime(customer);
    }

    @Transactional(readOnly = true)
    public OrderResponse find(Long id) {
        return toResponse(findEntity(id));
    }

    @Transactional
    public OrderResponse removeLine(Long id, Long lineId) {
        PurchaseOrder order = findEntity(id);
        order.removeLine(lineId);
        orders.flush();
        return toResponse(order);
    }

    @Transactional
    public OrderResponse rename(Long id, String customer) {
        PurchaseOrder order = findEntity(id);
        order.changeCustomer(customer);
        orders.flush();
        return toResponse(order);
    }

    @Transactional
    public void delete(Long id) {
        orders.delete(findEntity(id));
    }

    private PurchaseOrder findEntity(Long id) {
        return orders.findById(id)
                        .orElseThrow(() -> new NoSuchElementException("주문 없음"));
    }
}
```

**테스트 준비 코드**

테스트의 공통 부모 `FixtureSupport`는 테스트마다 UUID가 붙은 접두사(`prefix`)를 만들고, 그 접두사로 시작하는 데이터만 만들고 정리한다. 이렇게 하면 기존 데이터와 섞이거나 다른 테스트와 부딪히지 않는다. 테스트 클래스에는 `@Transactional`을 붙이지 않는다. 붙이면 테스트 전체가 하나의 트랜잭션이 되어 서비스의 커밋과 롤백을 확인할 수 없기 때문이다. 대신 서비스가 실제로 커밋하거나 롤백한 결과를 새 조회로 확인한다.

`FixtureSupport`는 메뉴 데이터도 준비하므로 메뉴 관련 클래스(`Menu`, `Category`, 두 리포지토리, `MenuService`)가 필요하다. 이 클래스들은 마지막 절에서 함께 설명한다.

**`src/test/java/com/ohgiraffers/practicaljpa/FixtureSupport.java`**

```java
package com.ohgiraffers.practicaljpa;

import com.ohgiraffers.practicaljpa.menu.*;
import com.ohgiraffers.practicaljpa.order.*;
import jakarta.persistence.*;
import org.junit.jupiter.api.*;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.data.domain.*;
import java.io.IOException;
import java.util.List;
import static org.junit.jupiter.api.Assertions.*;

@SpringBootTest
abstract class FixtureSupport {
    @Autowired protected OrderService orders;
    @Autowired protected OrderRepository orderRepository;
    @Autowired protected MenuService menus;
    @Autowired protected MenuRepository menuRepository;
    @Autowired protected EntityManagerFactory factory;

    // 클래스에 @Transactional을 붙이지 않는다.
    // 각 서비스 프록시가 실제로 커밋/롤백한 결과를 새 조회로 검증한다.
    @Autowired protected CategoryRepository categoryRepository;
    protected String prefix;
    protected Category category;
    protected java.util.List<Integer> fixtureCodes = new java.util.ArrayList<>();

    @BeforeEach
    // 테스트마다 UUID 표시가 붙은 메뉴 생성
    void prepareOwnFixtures() {
        // 기존 menu_name 길이에 맞춰 UUID 일부를 사용한다.
        prefix = "J7" + java.util.UUID.randomUUID().toString()
                .replace("-", "").substring(0, 16) + "-";
        category = categoryRepository.findAll().stream().findFirst()
                .orElseThrow(() -> new IllegalStateException("menudb의 기존 카테고리가 필요합니다."));
        for (Menu menu : menuRepository.saveAll(List.of(
                new Menu(prefix + "마늘빵", 2500, category),
                new Menu(prefix + "마늘크림빵", 4500, category),
                new Menu(prefix + "아메리카노", 3000, category)))) {
            fixtureCodes.add(menu.getMenuCode());
        }
    }

    @AfterEach
    void cleanupOwnFixtures() {
        // 이번 테스트의 UUID 표시가 붙은 주문과 직접 만든 메뉴 번호만 정리한다.
        for (PurchaseOrder order : orderRepository.findByCustomerStartingWith(prefix)) {
            orders.delete(order.getId());
        }
        for (Integer code : fixtureCodes) {
            menuRepository.deleteById(code);
        }
        fixtureCodes.clear();
    }

    protected long ownOrderCount() {
        return orderRepository.countByCustomerStartingWith(prefix);
    }

}
```

**cascade와 고아 객체 삭제 테스트**

`cascadePersistAndOrphanRemoval`은 주문을 만들면 항목 2개가 함께 저장되는지, 항목 하나를 삭제하면 1개가 남고 삭제된 항목 행이 데이터베이스에서 사라지는지(`em.find`가 `null`) 확인한다. 삭제 확인은 서비스와 다른 `EntityManager`를 만들어 데이터베이스를 직접 조회한다. `deletingParentAlsoDeletesOwnedLines`는 주문을 삭제하면 항목 행도 사라지는지 확인한다. 클래스 이름은 파일 이름(`OrderLifeCycleTests.java`)과 클래스 이름(`OrderLifecycleTests`)이 대소문자까지 다르지만 테스트 실행에는 영향이 없다.

**`src/test/java/com/ohgiraffers/practicaljpa/OrderLifeCycleTests.java`**

```java
package com.ohgiraffers.practicaljpa;

import com.ohgiraffers.practicaljpa.menu.*;
import com.ohgiraffers.practicaljpa.order.*;
import jakarta.persistence.*;
import org.junit.jupiter.api.*;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.data.domain.*;
import java.io.IOException;
import java.util.List;
import static org.junit.jupiter.api.Assertions.*;

class OrderLifecycleTests extends FixtureSupport {
    @Test
    void cascadePersistAndOrphanRemoval() {
        OrderService.OrderResponse created = orders.create(prefix + "학생");
        assertEquals(2, orders.find(created.id()).lines().size());
        Long removedId = created.lines().get(0).id();
        orders.removeLine(created.id(), removedId);
        assertEquals(1, orders.find(created.id()).lines().size());
        EntityManager em = factory.createEntityManager();
        try {
            assertNull(em.find(OrderLine.class, removedId));
        } finally { em.close(); }
    }

    @Test
    void deletingParentAlsoDeletesOwnedLines() {
        OrderService.OrderResponse created = orders.create(prefix + "학생");
        orders.delete(created.id());
        EntityManager em = factory.createEntityManager();
        try {
            for (OrderService.LineResponse line : created.lines()) {
                assertNull(em.find(OrderLine.class, line.id()));
            }
        } finally { em.close(); }
        assertEquals(0, ownOrderCount());
    }
}
```

## ☘️ 트랜잭션 롤백 규칙

`@Transactional`은 스프링이 서비스 객체를 감싼 **프록시**를 통해 동작한다. 프록시가 메서드 호출 전에 트랜잭션을 시작하고, 메서드가 정상적으로 반환하면 커밋하며, 예외가 프록시 밖으로 나오면 예외의 종류에 따라 롤백하거나 커밋한다. 이 구조에서 결과가 달라지는 다섯 가지 경우를 `OrderService`의 메서드와 테스트로 확인했다. 각 메서드는 주문을 저장(`saveAndFlush`)한 뒤 실패 상황을 만든다.

| 테스트                                                 | 서비스 메서드         | 상황                                                                   | 저장된 주문 수 |
| ------------------------------------------------------ | --------------------- | ---------------------------------------------------------------------- | -------------- |
| `runtimeRollback`                                      | `failRuntime`         | 런타임 예외(`IllegalStateException`)가 밖으로 전달된다.                | 0 (롤백)       |
| `checkedExceptionCommitsByDefault`                     | `failCheckedDefault`  | 체크 예외(`IOException`)가 밖으로 전달된다.                            | 1 (커밋)       |
| `rollbackForCheckedException`                          | `failCheckedRollback` | 같은 `IOException`이지만 `rollbackFor = IOException.class`를 지정했다. | 0 (롤백)       |
| `locallyCaughtBusinessExceptionDoesNotTriggerRollback` | `swallowFailure`      | 예외가 메서드 안에서 `catch`되어 밖으로 나오지 않는다.                 | 1 (커밋)       |
| `selfInvocationBypassesServiceTransaction`             | `selfInvocation`      | 같은 객체 안에서 `failRuntime`을 호출한다.                             | 1 (커밋)       |

**기본 규칙: 런타임 예외만 롤백한다**

스프링은 기본적으로 `RuntimeException`과 `Error`에서만 롤백하고, `IOException` 같은 체크 예외에서는 커밋한다. 체크 예외에서도 롤백하려면 `rollbackFor`로 지정해야 한다. 그렇지 않으면 예외가 발생했는데도 앞에서 저장한 내용이 데이터베이스에 남는다.

**예외를 삼키면 롤백되지 않는다**

`swallowFailure`는 메서드 안에서 예외를 `catch`한다. 프록시는 메서드가 정상 반환했다고 보므로 커밋한다. 업무 단계가 실패했는데도 일부 변경이 저장되는 결과가 된다. 실패를 처리하면서 롤백도 필요하다면 예외를 다시 던져야 한다.

**같은 객체 안의 호출은 프록시를 거치지 않는다**

`selfInvocation`은 `@Transactional`이 없고, 같은 클래스의 `failRuntime`을 호출한다. 이 호출은 프록시가 아니라 객체 자신(`this`)으로 직접 이어지므로 `failRuntime`에 붙은 `@Transactional`이 적용되지 않는다. 그 결과 서비스 수준의 트랜잭션이 없고, `saveAndFlush`는 `JpaRepository` 구현체가 가진 자체 트랜잭션에서 커밋된다. 이후 던져진 예외로는 이미 커밋된 저장을 되돌릴 수 없다. 테스트에서 예외는 `IllegalStateException`이 발생하지만 주문은 1건이 남는다.

## ☘️ JPA Auditing: 생성·수정 시각 자동 기록

테이블마다 생성 시각과 수정 시각 컬럼이 필요한 경우가 많다. 이를 엔티티마다 직접 채우는 대신 JPA Auditing이 저장과 수정 시점에 자동으로 기록하게 할 수 있다. 구성 요소는 다음과 같다.

- `@EnableJpaAuditing`: Auditing 기능을 켠다. 애플리케이션 클래스에 붙였다.
- `@MappedSuperclass`: 부모 클래스의 필드를 상속받는 엔티티의 테이블 컬럼으로 포함시킨다. 부모 클래스는 엔티티가 아니고 자신의 테이블이 없다.
- `@EntityListeners(AuditingEntityListener.class)`: 저장·수정 이벤트에 Auditing 리스너를 연결한다.
- `@CreatedDate`, `@LastModifiedDate`: 생성 시각과 마지막 수정 시각을 채울 필드를 표시한다.

`PurchaseOrder`가 `BaseTimeEntity`를 상속하므로 `practice_order` 테이블의 `created_at`, `updated_at`이 자동으로 채워진다.

## ☘️ 아직 완성되지 않은 동적 검색

이 챕터에는 조건을 조합해 메뉴를 검색하는 `Specification` 기능의 뼈대도 있다. `Specification`은 검색 조건을 객체로 만들어 `JpaSpecificationExecutor`로 실행하는 방식이다. 그러나 학습 코드는 라이브 코딩 전 단계에서 멈춰 있어 **동작하는 기능이 아니다**. 현재 상태는 다음과 같다.

- `MenuService.search`는 `UnsupportedOperationException("04 라이브 코딩 전입니다.")`을 던진다. 그래서 `GET /api/v1/practice/menus`를 호출해도 검색은 실행되지 않는다.
- `MenuSpecifications.search`는 키워드가 비어 있을 때만 조건 없음을 돌려주고, 키워드가 있으면 이름 `LIKE` 조건만 만든다. 최소·최대 가격과 카테고리 조건은 파라미터로 받지만 사용하지 않고, `conditions` 목록도 만들기만 하고 채우지 않는다.
- `provided-code/tests/04_DynamicSearchTests.java.txt`는 확장자가 `.txt`여서 컴파일되거나 실행되지 않는 제공용 파일이다.

그래서 위 8개 테스트 결과에는 동적 검색이 포함되지 않는다. 아래 코드는 현재 상태 그대로이며, 나머지 조건은 이후 단계에서 채워야 한다. `escapeLike`는 `%`와 `_`를 검색 패턴이 아닌 입력 문자로 다루기 위해 이스케이프 문자(`!`)를 붙이는 메서드다.

**`src/main/java/com/ohgiraffers/practicaljpa/menu/MenuSpecifications.java`**

```java
package com.ohgiraffers.practicaljpa.menu;

import org.springframework.data.jpa.domain.Specification;
import jakarta.persistence.criteria.Predicate;
import java.util.ArrayList;

public final class MenuSpecifications {

    private MenuSpecifications() {}

    public static Specification<Menu> search(String keyword, Integer minPrice,
                                              Integer maxPrice, Integer categoryCode) {
        // 이름 조건부터 한 단계씩 작성한다.
        /*
        * Root<Menu> : 조회할 Menu의 필드 지정
        * CriteriaQuery<?> : 쿼리 전체 설정
        * CriteriaBuilder : 비교 조건 생성
        * */
        return (root, query, cb) -> {
            ArrayList<Predicate> conditions = new ArrayList<>();
            if(keyword == null || keyword.isBlank()) {
                return cb.conjunction();
            }
            String pattern = "%" + escapeLike(keyword) + "%";
            return cb.like(root.get("menuName"), pattern, '!');
        };
    }

    // 문자열 처리 자체는 이전 학습 내용이므로 제공한다.
    // LIKE에서 %, _를 검색 패턴이 아닌 입력 문자로 취급하기 위한 처리다.
    static String escapeLike(String keyword) {
        return keyword.replace("!", "!!").replace("%", "!%").replace("_", "!_");
    }
}
```

## ☘️ 헷갈리기 쉬운 지점

- `orphanRemoval = true`로 부모 삭제가 자식에게 전파되지만 `cascade`에 `REMOVE`를 넣은 것은 아니다. 부모를 저장할 때 자식도 저장하려면 `cascade`에 `PERSIST`가 필요하다.
- `@Transactional` 메서드에서 체크 예외는 기본적으로 커밋된다. 롤백하려면 `rollbackFor`를 지정한다.
- 예외를 `catch`해서 삼키면 트랜잭션은 정상 종료로 처리된다.
- 같은 클래스 안에서 `@Transactional` 메서드를 직접 호출하면 트랜잭션이 적용되지 않는다. 다른 빈을 통해 호출하거나 호출 구조를 바꾸어야 한다.
- 트랜잭션 동작을 테스트할 때는 테스트 클래스에 `@Transactional`을 붙이지 않는다. 붙이면 서비스의 커밋과 롤백을 관찰할 수 없다.
