## ☘️ Java와 데이터베이스 연결하기

JDBC는 Java가 데이터베이스에 연결하고 SQL을 실행하는 공통 API다. DB별 드라이버가 실제 통신을 맡는다. 수업은 드라이버 준비 → Connection 획득 → SQL 준비·실행 → 결과 읽기 → 자원 해제 순서로 진행한다.

chap01은 Class.forName으로 MySQL 드라이버를 로딩하고 DriverManager.getConnection에 접속 정보를 주어 연결을 받는다. Connection은 Java 프로그램과 데이터베이스의 연결 통로다. 사용이 끝나면 close로 반납하고, 실패 시 null일 수도 있으므로 확인한다.

이 작업을 매번 쓰지 않도록 JDBCTemplate에 연결과 종료 기능을 모았다. Properties로 driver·url·계정 정보를 별도 설정에서 읽으므로 접속 설정과 실행 로직을 나누어 관리할 수 있다. 설정 파일을 읽는 FileReader는 try-with-resources로 닫고, Connection은 호출한 쪽에서 생명주기를 관리한다. 원본 getConnection은 실패를 기록하고 null을 반환할 수 있어 이후 코드가 무조건 연결 성공을 가정하면 별도 오류가 날 수 있다.

## ☘️ 조회 결과와 PreparedStatement

Statement는 완성된 SQL 문자열을 실행한다. Connection에서 만들고 SELECT는 executeQuery로 실행해 ResultSet을 받는다. ResultSet은 결과 행을 차례로 읽는 객체로, 처음에는 첫 행 앞에 있다. next를 호출해 다음 행으로 이동하고 행이 있으면 true가 된다. 그 상태에서 getString·getInt 등으로 현재 행의 열을 읽는다.

한 행 조회는 if(next), 여러 행은 while(next)를 사용한다. 열 이름 또는 위치로 읽을 수 있으며 수업은 열 이름으로 DTO 필드에 값을 옮겼다. 각 행마다 새 DTO를 만들어 List에 추가해야 개별 결과가 유지된다. 더 읽을 행이 없으면 반복이 끝난다. 자원은 결과 ResultSet → Statement → Connection 순으로 닫았다.

**값 바인딩**

PreparedStatement는 SQL 구조와 입력값을 분리한다. SQL에 `?`를 두고 prepareStatement로 준비한 뒤 setString·setInt로 각 위치에 값을 넣는다. 위치는 1부터이며 SQL의 물음표 순서와 맞춘다.

```java
String query = "SELECT MENU_NAME, MENU_PRICE FROM TBL_MENU WHERE MENU_CODE = ?";
pstmt = con.prepareStatement(query);
pstmt.setString(1, menuCode);
rset = pstmt.executeQuery();
```

수업의 이 코드는 메뉴 번호를 데이터로 전달한다. Statement처럼 완성 문자열을 실행할 때마다 전달하는 방식과 다르다. 이름 첫 글자 검색은 SQL의 CONCAT으로 바인딩한 값 뒤에 %를 붙였다. 직원 조회는 SQL을 XML의 이름별 항목으로 분리하고 Properties.loadFromXML로 읽어 사용했다. 이 XML은 실행 결과가 아니라 SQL 문장을 보관하는 파일이다.

원본 일부 조회는 예외가 나기 전에 List를 만들지 못하면 이후 for 순회에서 null 문제가 날 수 있다. Statement 단일 조회 파일에는 자원 해제도 빠져 있다. 다른 파일에 finally가 있다고 모든 실습 파일이 같은 정리를 했다고 가정하지 않는다.

## ☘️ SQL 인젝션을 비교한 이유

입력값을 SQL 문자열에 그대로 이어 붙이면 따옴표나 OR 조건이 데이터 대신 SQL 구문의 일부가 될 수 있다. 원본은 직원 번호·이름 조건에 조작된 이름 문자열을 넣어 원래 조회 의도와 다른 결과가 나오는 것을 비교했다. 이를 SQL 인젝션이라고 한다.

PreparedStatement는 직원 번호와 이름을 물음표 위치에 각각 바인딩한다. 조작된 문자열 전체를 이름이라는 값으로 다루므로 그 문자열의 OR가 SQL 조건으로 합쳐지지 않는다. 핵심은 SQL 구조와 값을 분리하는 것이다. 테이블명이나 정렬 구문 등 SQL 구조까지 입력 문자열로 직접 붙이는 별도 코드는 이 값 바인딩만으로 보호되지 않는다.

## ☘️ 메뉴 등록·수정·삭제

chap03은 XML에서 insertMenu·updateMenu·deleteMenu를 읽어 PreparedStatement로 실행한다. SELECT의 executeQuery와 달리 데이터 변경은 executeUpdate를 사용하고 영향을 받은 행 수를 int로 받는다. 이 숫자는 ResultSet이나 등록 객체 자체가 아니다. 0은 조건에 맞는 행이 없었던 경우일 수도 있으므로 항상 SQL 오류와 같은 뜻은 아니다.

고정 등록은 평양냉면·18000·분류 4·Y를 이름·가격·분류·판매 여부 순서로 넣는다. 입력 등록은 값을 MenuDTO에 묶은 뒤 같은 순서로 전달한다. nextInt 후 문자열을 받을 때는 남은 줄바꿈을 소비하고 판매 여부를 대문자로 바꾼다.

수정은 새 이름·새 가격·대상 코드 순서로, 삭제는 대상 코드 하나를 바인딩한다. Java에서 입력받은 순서와 SQL 물음표의 순서가 꼭 같은 것은 아니므로 SQL을 기준으로 맞춘다. finally에서 Statement와 Connection을 닫으며 자동 커밋 설정에서는 실행된 DML이 각자 확정된다. 여러 변경을 한 묶음으로 처리하려면 별도 트랜잭션 경계가 필요하다.

## ☘️ DAO로 접근 코드 분리하기

chap04의 첫 파일은 카테고리 조회·사용자 입력·값 가공·SQL 실행을 main에 함께 둔다. DAO는 Database Access Object로, 데이터베이스 접근 코드를 모으는 객체다. 역할을 나누면 입력 화면을 바꾸더라도 SQL 처리 코드를 같은 방식으로 사용할 수 있다.

MenuDAO는 생성자에서 SQL XML을 읽고, selectAllCategory에서 조회 결과를 CategoryDTO 목록으로 변환한다. insertNewMenu는 Connection과 MenuDTO를 받아 값을 바인딩하고 변경 행 수를 반환한다. DAO 안에는 사용자 입력이나 성공 안내 출력이 없다.

호출부는 연결을 만들고 카테고리를 보여 준 뒤 입력을 DTO로 묶어 DAO를 호출한다. DAO는 자신이 만든 ResultSet·PreparedStatement만 닫고 전달받은 Connection은 닫지 않는다. 호출부가 여러 작업에 같은 연결을 쓰고 마지막에 닫을 수 있게 소유 책임을 나눈 것이다.

원본은 “예” 이외의 모든 답을 N으로 바꾸며, 입력 코드가 조회 목록에 있는지 별도로 검증하지 않는다. DAO도 SQL 예외를 기록하고 0을 반환해 호출자가 실패 원인과 0행 결과를 구분하기 어렵다. 계층을 나눈 것과 입력 검증·오류 전달까지 완성된 것은 구분해 복습한다.
