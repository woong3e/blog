## 🍀 과제 1에서 리마인드할 부분

이번 과제에서 중요했던 부분은 **컴포넌트의 역할을 분리하고 상태를 어디에서 관리할지 결정하는 것**이었다.

`SearchBox`는 사용자의 입력값만 관리하고 검색이 발생하면 부모에게 값을 전달한다.
실제 검색 결과가 무엇인지는 알 필요가 없다.

반대로 `ImageBox`는 API 요청이나 검색 로직을 직접 처리하지 않고, 부모로부터 전달받은 `imgURL`에 따라 화면만 렌더링한다.

실제 데이터와 검색 상태는 부모인 `App`에서 관리한다.

```js
<SearchBox handleClick={handleClick} />
<ImageBox keyword={keyword} isLoading={isLoading} imgURL={imgURL} />
```

즉,

**부모는 상태와 로직을 관리하고, 자식은 필요한 값을 props로 전달받아 자신의 역할에 집중하도록 컴포넌트를 분리했다.**

또 하나 기억할 부분은 객체의 **동적 프로퍼티 접근**이다.

GitHub Emoji API의 응답은 다음과 같이 이모지 이름이 key인 객체 형태이다.

```js
{
  "+1": "https://...",
  "100": "https://...",
  "smile": "https://..."
}
```

검색어가 변수 `keyword`에 들어 있기 때문에 점 표기법이 아니라 대괄호 표기법을 사용해야 한다.

```js
const imgURL = emojiList?.[keyword]
```

`?.`를 사용하면 `emojiList`가 `null` 또는 `undefined`인 경우에도 오류를 발생시키지 않고 `undefined`를 반환한다.

리마인드

- `useEffect(..., [])`는 컴포넌트가 처음 렌더링될 때 API 데이터를 가져오는 용도로 사용할 수 있다.
- 입력값처럼 컴포넌트 내부에서 사용하는 값은 `useState`로 관리할 수 있다.
- 여러 컴포넌트가 함께 사용해야 하는 상태는 공통 부모에서 관리하는 것이 자연스럽다.
- 부모 → 자식으로 데이터나 함수를 전달할 때 `props`를 사용한다.
- 객체의 key가 변수라면 `obj[key]` 형태로 접근한다.
- 컴포넌트가 모든 로직을 직접 처리하기보다 역할을 나누는 것이 중요하다.

> **핵심:** 상태를 어느 컴포넌트가 소유해야 하는지 판단하고, 필요한 데이터와 함수를 props를 통해 전달하는 흐름을 이해하는 과제였다.

## 🍀 과제 2에서 리마인드할 부분

이번 과제에서 가장 중요했던 부분은 **여러 비동기 요청을 동시에 처리하고 그 결과를 하나로 모으는 과정**이었다.

목록 API를 요청하면 바로 이미지 정보가 오는 것이 아니라 각 포켓몬의 상세 정보를 가져올 수 있는 URL이 전달된다.

```js
listData.results
```

따라서 목록을 가져온 뒤 다시 각각의 상세 URL에 요청을 보내야 했다.

```js
const detailPromises = listData.results.map((pokemon) => {
  return fetch(pokemon.url).then((response) => {
    if (!response.ok) {
      throw new Error('포켓몬 상세 정보를 불러오지 못했습니다.')
    }

    return response.json()
  })
})
```

여기서 `map()`의 반환값이 중요한데, `fetch()`의 반환값은 Promise이므로 결과적으로 다음과 같은 배열이 만들어진다.

```js
[Promise, Promise, Promise, ...]
```

즉 아직 포켓몬 데이터가 들어 있는 것이 아니라 **각 API 요청의 완료를 기다리고 있는 Promise들이 들어 있는 배열**이다.

이 Promise들을 실제 데이터 배열로 바꾸기 위해 `Promise.all()`을 사용한다.

```js
const pokemons = await Promise.all(detailPromises)
```

`Promise.all()`은 전달받은 모든 Promise가 resolve될 때까지 기다린 뒤 각각의 결과를 같은 순서의 배열로 반환한다.

```js
[Promise, Promise, Promise]
        ↓ Promise.all()
[pokemon1, pokemon2, pokemon3]
```

그 이후에야 React 상태에 실제 데이터를 저장할 수 있다.

```js
setPokemons(pokemons)
```

Promise.all에서 기억할 점

`Promise.all()`은 여러 비동기 작업을 함께 처리할 때 유용하지만 **하나라도 reject되면 전체 `Promise.all()`도 reject된다.**

따라서 모든 요청이 성공해야 정상적으로 화면을 구성할 수 있는 상황에 적합하다.

```js
try {
  const pokemons = await Promise.all(detailPromises)
  setPokemons(pokemons)
} catch (error) {
  setError(error)
}
```

또한 `fetch()`는 404나 500 같은 HTTP 오류가 발생했다고 해서 자동으로 reject되지 않는다.

따라서 직접 `response.ok`를 확인해야 한다.

```js
if (!response.ok) {
  throw new Error('에러')
}
```

`throw`로 발생시킨 에러는 `catch`에서 처리할 수 있고, 성공 여부와 관계없이 실행되어야 하는 로딩 상태 변경은 `finally`에서 처리할 수 있다.

```js
try {
  // API 요청
} catch (error) {
  setError(error)
} finally {
  setLoading(false)
}
```

리마인드

- `fetch()`의 반환값은 Promise이다.
- `map()`에서 `fetch()`를 반환하면 Promise 배열이 만들어진다.
- `Promise.all()`은 Promise 배열을 받아 모든 요청의 완료를 기다린다.
- `Promise.all()`은 하나라도 reject되면 전체가 reject된다.
- `fetch()`는 HTTP 오류를 자동으로 reject하지 않기 때문에 `response.ok` 확인이 필요하다.
- 비동기 작업의 성공/실패는 `try-catch`, 항상 실행할 처리는 `finally`로 관리할 수 있다.
- API 목록 데이터에 필요한 정보가 없다면 상세 API를 추가로 요청해야 할 수 있다.

> **핵심:** `목록 API 요청 → 상세 URL 추출 → Promise 배열 생성 → Promise.all() → 실제 데이터 배열 → 상태 저장`이라는 비동기 데이터 처리 흐름을 이해하는 과제였다.
