오늘은 렌더링 중 계산과 참조를 다루는 `useMemo`, `useCallback`, 값을 유지하거나 DOM에 접근하는 `useRef`, 로직을 재사용하는 커스텀 Hook을 공부했다. 비동기 작업에서는 중첩 콜백을 Promise 체인으로 바꾸고 성공·실패·종료 처리를 연결했다.

## 계산 결과와 함수 참조 기억하기

**useMemo는 계산 결과를 재사용한다**

계산기 예제에서는 `hardNumber`, `easyNumber`를 별도 state로 관리했다. 컴포넌트가 렌더링될 때 함수를 바로 호출하면 어떤 state가 바뀌었는지와 관계없이 계산이 다시 실행된다.

```jsx
const hardSum = useMemo(() => hardCalculator(hardNumber), [hardNumber])
const easySum = easyCalculator(easyNumber)
```

`useMemo`는 의존성이 같으면 앞서 계산한 값을 재사용한다. 따라서 `easyNumber`만 바뀌었을 때 `hardCalculator`의 재실행을 줄일 수 있다. 컴포넌트의 렌더링 자체를 막는 기능은 아니다.

원본 `hardCalculator`는 반복문 안에서 바로 `return`해서 첫 반복에 종료된다. 반복 횟수를 크게 적었어도 실제로 오래 걸리는 계산은 아니다. 이 예제는 계산 호출 여부를 로그로 비교하는 용도로 이해하고, 실제 성능 효과를 확인하려면 계산량과 실행 시간을 따로 측정해야 한다.

**객체의 내용과 참조는 다르다**

위치 예제에서는 `number`만 바뀌어도 컴포넌트 내부의 `location` 객체가 새로 만들어졌다. 국가 문자열이 같더라도 새 객체는 이전 객체와 다른 참조이므로 `[location]`을 의존성으로 둔 Effect가 다시 실행된다.

```jsx
// 렌더링할 때마다 새 객체
const location = { country: isKorea ? '한국' : '외국' }

// 의존성이 같을 때 이전 계산 결과 재사용
const location = useMemo(() => ({ country: isKorea ? '한국' : '외국' }), [isKorea])
```

두 코드는 적용 전·후를 비교한 것으로 동시에 선언하는 코드는 아니다. 이 실습의 핵심은 내용이 같은 객체도 참조가 다르면 다른 의존성으로 비교된다는 점이다.

**useCallback은 함수를 실행하지 않고 함수 참조를 재사용한다**

```jsx
const printNumber = useCallback(() => {
  console.log(`current number: ${number}`)
}, [number])

useEffect(() => {
  console.log('printNumber 함수가 변경됐다.')
}, [printNumber])
```

일반 함수는 렌더링할 때마다 새로 생성되지만, `useCallback`은 의존성이 같으면 기존 함수 참조를 반환한다. 숫자와 무관한 토글 state를 바꿔도 `printNumber`를 의존성으로 둔 Effect의 불필요한 재실행을 줄일 수 있다.

사각형 실습에서도 스타일 생성 함수 `genSquareStyle`을 `[size]`와 함께 `useCallback`으로 감쌌다. 테마만 바꾸면 함수 참조가 유지되어 자식의 스타일 변경 Effect가 다시 실행되지 않는다. 다만 부모가 렌더링될 때 자식도 렌더링될 수 있으므로, **Effect 재실행을 줄이는 것과 자식 렌더링을 생략하는 것은 구분해야 한다.**

**상품 검색 실습에서 발견한 오류**

검색창의 `inputText`와 실제 검색에 적용한 `query`를 구분했다. 타이핑할 때는 입력값만 바뀌고 검색 버튼을 눌러야 `query`가 바뀌는 구조였다.

원본 `filter()` 콜백은 중괄호 안에서 `includes()`를 호출한 뒤 결과를 반환하지 않았다. 모든 항목이 `undefined`를 반환하므로 검색 결과는 항상 빈 배열이 된다. 과제 요구사항인 앞뒤 공백과 대소문자 처리도 추가해야 한다.

```jsx
// 원본 실습을 보완한 핵심 코드
const searchProducts = useCallback((nextQuery) => {
  setQuery(nextQuery)
}, [])

const filteredProducts = useMemo(() => {
  console.log('상품 목록 다시 계산')
  const normalizedQuery = query.trim().toLowerCase()

  return PRODUCTS.filter((product) => product.name.toLowerCase().includes(normalizedQuery))
}, [query])
```

`searchProducts`는 현재 `query`를 읽지 않고 인자로 받은 값을 setter에 전달한다. 원본의 `[query]` 의존성은 필요하지 않으므로 위 개선 예시에서는 `[]`로 두었다. React의 state setter는 안정적인 참조를 가진다.

## useRef와 커스텀 Hook

**state, 지역 변수, ref의 차이**

카운터 예제에서 세 가지 방식으로 숫자를 보관하며 차이를 비교했다.

| 방식                    | 렌더링 사이에 값 유지 | 값 변경으로 렌더링 요청 |
| ----------------------- | --------------------- | ----------------------- |
| 컴포넌트 내부 지역 변수 | 다시 실행할 때 초기화 | 없음                    |
| `useState`              | 유지                  | setter로 변경하면 요청  |
| `useRef`                | `.current`에 유지     | 없음                    |

`countRef.current += 1`은 저장된 값을 바꾸지만 화면을 다시 그리도록 요청하지 않는다. 버튼 클릭 뒤 콘솔의 ref 값은 바뀌어도 화면은 즉시 바뀌지 않는다. 화면에 보여줘야 하는 데이터는 state로 관리하고, 타이머 id나 DOM 요소처럼 렌더링에 직접 필요하지 않은 값은 ref로 관리한다.

원본은 차이를 관찰하려고 `countRef.current`도 JSX에 출력했다. 실제 화면 데이터를 ref에서 읽는 방식보다는 state를 사용하는 것이 적절하다.

**입력칸에 포커스 주기**

로그인 예제에서는 아이디 input에 ref를 연결하고 마운트 후 해당 DOM 요소의 `focus()`를 호출했다. 로그인 버튼을 누른 뒤에도 입력값을 비우고 아이디 칸으로 포커스를 돌렸다.

```jsx
const usernameRef = useRef(null)

useEffect(() => {
  usernameRef.current?.focus()
}, [])

return <input ref={usernameRef} />
```

React가 input DOM을 생성한 뒤 ref의 `.current`에 그 요소를 연결한다. 입력값을 state로 관리하는 것과 DOM에 포커스를 주는 것은 목적이 다르다.

**커스텀 Hook은 상태를 사용하는 로직을 재사용한다**

일정 시간 뒤 준비 완료 상태가 되는 `useDelayTimer`와 `useDelayReady`를 만들었다. state와 Effect를 Hook 안으로 모으면 컴포넌트는 반환된 `isReady`로 화면만 선택할 수 있다.

```jsx
// 대기 시작 시 초기화하고 cleanup은 타이머를 해제하도록 정리한 예시
function useDelayReady(delay) {
  const [isReady, setIsReady] = useState(false)

  useEffect(() => {
    setIsReady(false)
    const timerId = setTimeout(() => setIsReady(true), delay)
    return () => clearTimeout(timerId)
  }, [delay])

  return isReady
}
```

원본 통합 실습에서는 `setIsReady(false)`를 cleanup에 넣었다. 위 예시처럼 새로운 대기를 시작하는 setup에서 상태를 초기화하고 cleanup에서는 이전 타이머를 해제하면 역할이 분명해진다. `setTimeout`의 시간 단위는 밀리초이므로 `3000`은 3초이다.

커스텀 Hook의 이름은 `use`로 시작하고, 컴포넌트나 다른 Hook의 최상위에서 호출한다. 여러 컴포넌트가 같은 Hook을 사용해도 상태가 하나로 공유되는 것은 아니다. 각 호출은 독립적인 상태를 가지면서 같은 로직을 재사용한다.

## 중첩 콜백에서 Promise 체인으로

비동기 예제에서는 햄버거를 주문하고 `setTimeout`으로 3초 뒤 메시지를 출력하도록 예약했다. 다음 줄의 감자튀김 주문은 타이머가 끝날 때까지 기다리지 않고 실행된다.

이후 “1초 뒤 숫자에 10을 더하기”를 세 번 이어서 실행했다. 앞선 결과를 다음 작업에 넘기려면 콜백을 중첩해야 했고, 단계가 늘어날수록 코드가 안쪽으로 깊어졌다.

**Promise는 앞으로 정해질 결과를 나타낸다**

Promise는 대기 중인 `pending`, 성공한 `fulfilled`, 실패한 `rejected` 상태를 가진다. 성공하면 `resolve`로 결과를 전달하고 실패하면 `reject`로 이유를 전달한다.

```js
function addAfterOneSecond(number) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      const result = number + 10

      if (result > 30) {
        reject(new Error('30을 초과했습니다.'))
        return
      }

      resolve(result)
    }, 1000)
  })
}

addAfterOneSecond(0)
  .then((number) => {
    console.log(number) // 10
    return addAfterOneSecond(number)
  })
  .then((number) => {
    console.log(number) // 20
    return addAfterOneSecond(number)
  })
  .then((number) => {
    console.log(number) // 30
    return addAfterOneSecond(number)
  })
  .catch((error) => console.log(error))
  .finally(() => console.log('작업 종료'))
```

`10 → 20 → 30`을 출력하고, 다음 작업의 결과 `40`은 조건을 넘어서 실패한다. 실패는 `.catch()`로 이어지고 마지막에 `.finally()`가 실행된다. 원본은 Error 객체를 출력했으며 메시지만 보여주고 싶다면 `error.message`를 사용하면 된다.

여기서 가장 중요한 것은 **각 `.then()`에서 다음 Promise를 반환하는 것**이다. 반환한 Promise가 끝나야 다음 `.then()`이 그 결과를 받는다. `return`을 빠뜨리면 다음 작업을 기다리는 연결이 끊기고 다음 핸들러에 `undefined`가 전달될 수 있다.

- `useMemo`는 계산 결과, `useCallback`은 함수 참조를 재사용한다.
- 의존성은 콜백 안에서 실제로 읽는 값을 기준으로 작성한다.
- ref 값 변경은 렌더링을 요청하지 않으므로 화면 데이터와 구분한다.
- 커스텀 Hook은 로직을 재사용하고 각 호출의 state는 독립적이다.
- Promise 체인은 반환값으로 이어지며 오류는 `catch`, 공통 종료 처리는 `finally`에 작성한다.
