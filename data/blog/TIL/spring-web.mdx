## ☘️ chap00 Spring Boot 시작

`@SpringBootApplication`과 `SpringApplication.run()`으로 애플리케이션을 실행한다. `@RestController`의 `@GetMapping("/hello")`는 GET 요청을 메서드에 연결하고 반환 문자열을 HTTP 응답 본문으로 보낸다.

**요청 한 건의 흐름**

서버를 실행한 뒤 브라우저나 HTTP 파일에서 `GET /hello`를 보내면 `/hello`에 연결된 `hello()`가 실행된다. 메서드의 `"Spring Boot Hello"`가 화면 템플릿 이름이 아니라 응답 본문으로 전달된다. 이것이 이후 API 예제의 출발점이다.

## ☘️ chap01 요청 매핑과 chap02 핸들러

`@RestController`는 컨트롤러와 응답 본문 기능을 합친다. 클래스의 `@RequestMapping`으로 공통 주소를 지정하고 `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping`으로 HTTP 요청을 핸들러 메서드에 연결한다. 등록 예제는 `ResponseEntity`로 201을 반환했다.

```java
@GetMapping("/{menuCode}")
public ResponseEntity<Map<String, Object>> findMenu(@PathVariable int menuCode) {
    Map<String, Object> response = new LinkedHashMap<>();
    response.put("menuCode", menuCode);
    return ResponseEntity.ok(response);
}
```

`@RequestParam`은 쿼리 문자열을 받는다. 이름을 생략하면 Java 매개변수명을 사용하며, `required = false`는 누락을 허용하고 `defaultValue`는 기본값을 정한다. Map으로 전체 쿼리 값을 받을 수도 있다. `@PathVariable`은 경로 값을 받는다.

`@RequestBody`는 JSON 본문을 같은 프로퍼티 이름의 DTO로 변환하거나 문자열 본문을 그대로 받는다. 잘못된 JSON이나 빈 본문은 400, 지원하지 않는 Content-Type은 415가 발생할 수 있다. `@RequestHeader`는 헤더를, `@CookieValue`는 쿠키를 받으며 선택값은 `required = false`로 지정한다. null이 가능한 응답에는 `LinkedHashMap`을 사용했다.

**요청값이 메서드로 들어오는 예**

`GET /api/v1/menus?keyword=coffee&categoryCode=2&page=1`에서는 `keyword`, `categoryCode`, `page`가 각각 해당 매개변수로 들어간다. 쿼리를 생략하면 선택값 `keyword`는 null이고, 기본값이 지정된 `categoryCode`와 `page`는 각각 0과 1이다. `/menus/3`에서는 경로의 3을 `@PathVariable`이 `menuCode`에 전달한다.

메뉴 등록 요청은 `Content-Type: application/json`과 함께 `name`, `price`, `categoryCode`가 담긴 본문을 보낸다. `@RequestBody MenuDTO`가 이를 객체로 받아 응답 Map에 담고 201을 반환한다. `/raw` 예제는 DTO 대신 `String`으로 본문을 받고 Content-Type 헤더를 함께 확인한다. 요청 정보 예제는 전체 헤더와 `user-agent`, `clientId` 쿠키를 읽는다.

## ☘️ chap03 Jackson과 JSON

Java `List`는 JSON 배열로, DTO는 JSON 객체로 직렬화된다. `@RequestBody`는 JSON을 DTO로 역직렬화한다. 바깥 Map에 List를 넣으면 객체 안에 배열이 중첩된다.

`@JsonProperty("memberNo")`는 Java의 `no`와 JSON의 `memberNo`를 연결한다. `@JsonFormat(pattern = "yyyy-MM-dd")`은 날짜 형식을 지정하며 형식이 맞지 않으면 역직렬화에 실패할 수 있다. `ObjectMapper`를 이용한 직접 변환도 확인했다.

**직렬화와 역직렬화 따라가기**

회원 목록을 반환하면 Java의 `List<MemberDTO>`가 JSON 배열이 되고 각 회원은 배열 안의 객체가 된다. 회원 하나를 반환하면 JSON 객체 하나다. 반대로 등록 요청의 JSON은 `@RequestBody`를 통해 `MemberDTO`가 되고 목록에 추가된다. 응답을 보낼 때 그 객체는 다시 JSON으로 변환된다.

예를 들어 Java 필드 이름은 `no`지만 `@JsonProperty("memberNo")`를 지정하면 요청과 응답의 JSON에서는 `memberNo`를 사용한다. `LocalDate`의 `@JsonFormat`은 `2026-04-24`처럼 지정한 형식으로 주고받도록 한다. ObjectMapper 예제는 객체를 JSON 문자열로 직접 바꾸는 결과도 확인한다.

## ☘️ chap04 예외 처리

`@RestControllerAdvice`에서 컨트롤러의 예외를 공통으로 처리하고 `@ExceptionHandler`가 예외 타입별 응답을 만든다. 조회 대상이 없을 때 404, 잘못된 입력이나 요청 본문은 400, 예상하지 못한 오류는 500으로 처리하는 예제다. 오류 응답에는 상태, 메시지, 경로 등을 담고 예상하지 못한 원인은 서버 로그에 남긴다. `@Valid`, `@Min`, `@NotBlank`로 요청값을 검사한다.

원본 코드의 검증 오류 응답은 상태 값 400과 `BAD_GATEWAY` 문구가 함께 쓰이고, 경로에서 제거하는 `uri =` 문자열도 요청 설명의 `uri=`와 다르다. 서버 오류 테스트 메서드도 컨트롤러가 아닌 advice 클래스에 작성돼 있다.

**예외가 응답으로 바뀌는 과정**

회원 조회에서 찾는 번호가 없으면 `MemberNotFoundException`을 던진다. `@RestControllerAdvice`의 해당 `@ExceptionHandler`가 이를 받아 `ErrorResponse`를 만들고 404로 응답한다. 등록 시 필수 값이나 최솟값 검사에 실패하면 검증 예외를 처리해 400을 돌려준다. 예상하지 못한 예외는 로그에 원인을 기록하고 클라이언트에는 500 응답을 보낸다.

실습의 오류 응답에는 발생 시각, 상태, 오류 이름, 메시지, 요청 경로가 담긴다. 프론트엔드는 같은 구조에서 상태와 메시지를 확인할 수 있다.

## ☘️ chap05 파일 업로드

`MultipartFile`을 `@RequestParam("file")`로 받고 FormData의 키와 이름을 맞춘다. 여러 파일은 `List<MultipartFile>`로 받는다. 업로드 기준 경로를 정규화하고 단일·다중 업로드 디렉터리를 만든 뒤 파일명과 빈 파일 여부를 확인한다.

UUID와 원본 확장자로 저장명을 만들고 `transferTo`로 저장한다. 응답에는 업로드 루트 기준 상대 경로를 담는다. 다중 업로드가 중간에 실패하면 앞서 저장한 파일을 정리하고 원래 예외를 다시 던진다. 정리 오류는 원래 예외의 부가 정보로 남긴다.

**파일 한 개가 저장되는 순서**

클라이언트가 `file`과 선택사항인 `description`을 multipart 요청으로 보낸다. 서버는 파일이 비어 있거나 원본 이름이 없는지 검사한다. 원본 파일명에 `..`이 포함되면 거부하고 파일명만 추출한다. 이후 UUID와 확장자로 저장 이름을 만들고 정규화한 저장 경로가 업로드 디렉터리 안에 있는지 확인한 뒤 파일을 쓴다.

다중 업로드는 파일을 하나씩 같은 방식으로 저장한다. 두 번째 파일에서 실패했다면 이미 저장된 첫 번째 파일을 정리하려고 시도한 뒤 최초 예외를 다시 전달한다.

## ☘️ chap06 인터셉터

인터셉터는 컨트롤러 앞뒤의 공통 로직을 처리한다. `preHandle()`은 컨트롤러 전에 실행하며 false면 처리를 중단한다. `postHandle()`은 정상 실행 후 호출되며 예외 시 호출되지 않을 수 있다. `afterCompletion()`은 요청이 끝난 뒤 마무리 작업에 쓴다.

`WebMvcConfigurer.addInterceptors()`에 등록하면서 경로와 순서를 지정한다. 실습에서는 처리 시간을 측정하고 관리자 경로의 `X-API-KEY`를 검사했다. 거부할 때는 인터셉터에서 401 상태와 JSON 본문을 직접 작성한다.

**관리자 요청 예제**

`/api/v1/**`에는 처리 시간을 재는 인터셉터가 먼저 적용되고, `/api/v1/admin/**`에는 API 키 검사도 적용된다. 관리 요청에서 헤더 값이 일치하면 `preHandle()`이 true를 반환해 다음 단계로 진행한다. 키가 없거나 다르면 false를 반환하고, 컨트롤러 대신 인터셉터가 상태 코드와 JSON 오류를 쓴다. 시간 측정 예제는 요청 시작과 종료 시점을 사용한다.

## ☘️ chap07 React 연동

서버는 `/api/**`에 대해 `http://localhost:3000`을 허용한다. 클라이언트는 환경 변수의 API 주소로 메뉴 목록을 `fetch`하고 로딩·오류 상태를 표시한다. 등록 시 JSON을 POST하고 서버가 돌려준 메뉴를 기존 배열 뒤에 추가해 상태를 갱신한다. `preventDefault()`는 폼의 기본 새로고침을 막는다.

**화면과 서버 사이의 흐름**

화면이 처음 표시되면 `useEffect`에서 메뉴 목록을 요청하고, 성공하면 응답 JSON을 상태에 담아 목록을 그린다. 실패하면 오류 문장을 표시하고 요청이 끝나면 로딩 상태를 해제한다. 등록 버튼은 입력한 이름과 숫자로 바꾼 가격을 JSON으로 보낸다. 성공 응답으로 받은 메뉴를 기존 목록에 더하고 입력값을 비운다.

클라이언트는 3000번 포트, 서버는 8080번 포트를 사용한다. 서버의 CORS 설정은 `/api/**`에 대해 해당 클라이언트 출처와 GET·POST·OPTIONS, Content-Type 헤더를 허용한다.

## ☘️ chap08 REST API

요청 DTO에는 등록·수정 입력값을, 응답 DTO에는 공개할 회원 정보만 담고 비밀번호를 제외한다. `ResponseEntity.created(URI)`는 201과 Location 헤더를, `noContent().build()`는 본문 없는 204를 만든다.

`@Valid`와 `@NotBlank`, `@NotNull`, `@Size`, `@Past`로 입력을 검사하고 예외 처리기에서 필드 오류에 맞는 응답을 만든다. 수업 코드에서 비밀번호 최대 길이는 10, 이름 최대 길이는 5다. Swagger 예제는 `@Operation`, `@ApiResponse`, `@Schema`와 OpenAPI 설정으로 API와 응답·요청 필드를 문서화한다.

**검증과 문서화 흐름**

+회원 등록 JSON이 `@Valid @RequestBody`에 들어오면 DTO의 제약 조건을 검사한다. 공백 아이디나 이름은 `@NotBlank`, 누락된 가입일은 `@NotNull`, 미래 가입일은 `@Past` 검사 대상이다. 실패하면 `MethodArgumentNotValidException`을 받아 첫 필드 오류의 코드와 메시지로 400 응답을 구성한다. 존재하지 않는 회원을 찾는 예제는 별도 예외와 404를 사용한다.

+Swagger 예제에서는 `@Operation`으로 요청의 기능을 설명하고 `@ApiResponse`로 응답 코드를 표시한다. `@Schema`는 요청 필드의 설명과 예시를 붙인다. 이 정보는 Swagger UI에서 API를 살펴볼 때 사용된다.
