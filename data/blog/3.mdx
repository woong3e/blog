# 🍀 1.1. 테스트가 당신의 코드에 미치는 영향

테스트란 애플리케이션의 품질과 안정성을 높이기 위해 사전에 결함을 찾아내고 수정하기 위한 행위이다.

주로 특정 모듈(특히 컴포넌트)이 사양에 잘 동작하는지 자동화된 테스트로 검증한다.

**테스트 코드의 효과**

1. 좋은 설계에 대한 사고를 도와준다. 결합도가 높으면 테스트 복잡도가 향상된다. 이러한 문제를 해결하기 위해 테스트 단위를 어떻게 나눌지 고민하다보면 컴포넌트 간 의존성을 줄이기 위해 올바른 설계가 무엇일지 고민하게 된다.

2. 테스트 코드를 기반으로 바르고 안정적이게 리팩토링 할 수 있다.
   ![테스트코드 리팩토링](/static/images/blog02/screenshot1.png)

3. 좋은 테스트 코드는 애플리케이션의 이해를 돕는 문서가 된다. 단순히 버그를 잡는 도구를 넘어서 가장 신뢰할 수 있는 최신 명세서가 될 수 있다.

# 🍀 1.2. 올바른 테스트 작성을 위한 규칙

1. 인터페이스를 기준으로 테스트를 작성하자
   ![잘못된 테스트코드](/static/images/blog02/screenshot2.png)

   ❌ 변경되는 상태가 많은 경우 테스트 코드 상에서 일일이 직접 변경해야 하며 어떤 상황에서 변경 되는 것인지 드러나지 않음

   ❌ 내부 상태나 변수값을 기준으로 검증하다 보니 어떤 것을 검증하는지 테스트 코드만 보고 한 눈에 파악하기 어려움

   ❌ 내부 구현을 검증하려다 보니 구현에 종속적인 테스트 코드가 양산됨. 상태나 변수명이 하나라도 바뀌면 테스트 코드 모두를 바꿔야 함. 즉, 캡슐화를 위반하는 코드가 된다.

   ![잘못된 테스트코드](/static/images/blog02/screenshot3.png)

   ⭕️ 내부 구현과 종속성이 없으며 캡슐화에 위반되지 않음

   ⭕️ 어떤 행위를 하는지 명확해짐

   ⭕️ 테스트를 설명하기 위한 불필요한 주석이나 설명 또한 없음

2. 커버리지 보다는 의미있는 테스트인지 고민하자

   100% 커버리지를 위한 테스트보다는 의미있는 테스트인지, 어떤 범위까지 검증해야 효율적인 테스트가 될지를 고민해야 한다.

3. 테스트 코드도 유지 보수의 대상! 가독성을 높이자

- 테스트 하고자 하는 내용을 명확하게 적자

- 하나의 테스트에서는 가급적 하나의 동작만 검증하자

# 🍀 2.1. 단위 테스트란 무엇일까?

1. 단위 테스트란 앱에서 테스트 가능한 가장 작은 소프트웨어를 실행해
   예상대로 동작하는지 확인하는 테스트이다.

   프론트엔드에서의 단위 테스트는 단일 함수의 **결괏값** 또는 단일 컴포넌트(클래스)의 **상태(UI)나 행위**를 검증한다.

2. 공통 컴포넌트는 단위 테스트에 적합하다

- 다른 컴포넌트와의 상호작용이 없으며

- 컴포넌트 내부 비즈니스 로직을 기능 단위로 나눠 검증하기 좋다

- 범용적으로 재사용 되기 때문에 단위 테스트를 통해 안정성을 높여야 한다

3. **Arrange-Act-Assert(AAA) 패턴**

- Arrange: 테스트를 위한 환경 만들기(컴포넌트 렌더링)

- Act: 테스트할 동작 시뮬레이션(클릭, 타이핑, 메서드 호출)

- Assert: 기대 결과대로 실행되었는지 검증

# 🍀 2.2. 테스트 환경과 매처

- vitest는 기본적으로 vite의 설정을 따른다. vite.config.ts 파일의 test 필드에 작성하면 되고 vitest.config.ts 파일에 별도로 분리하여 관리할 수도 있다.

- test 필드에 globals 옵션을 true로 설정하면 vitest에서 제공하는 api들을 별도의 import없이 사용할 수 있다.

- environment 옵션을 jsdom환경에서 구동하도록 설정하고 setupFiles 옵션을 setupTests.js를 보고 동작하도록 설정해두었다.

- [vitest config 공식문서 참고](https://vitest.dev/config/)

- jsdom이란 Node.js 환경에서 사용할 수 있도록 자바스크립트로 구현한 가상 브라우저(DOM)이다.

- 테스트하려는 컴포넌트가 jsdom에서 어떻게 렌더링 되는지 DOM 구조를 확인하고 싶다면 screen.debug()을 사용하여 터미널에서 구조를 확인할 수 있다.

- describe 함수는 관련있는 함수들을 그룹화하는 역할은 한다.

- expect 함수를 사용하면 검증대상에 대한 다양한 단언을 사용할 수 있다.

- **단언(Assertion)** 이란 테스트가 통과하기 위한 조건을 기술하여 검증을 실행하는 것이다.

- 매처란 기대 결과를 검증하기 위해 사용되는 일종의 API 집합

- vitest에서는 기본적으로 자바스크립트 논리를 검증하는 매처만 내장하고 있다. DOM과 관련된 매처를 사용하기 위해서 testing-library/jest-dom 으로 확장해서 사용한다.

- toBeInTheDocument()는 특정 요소가 현재 DOM 상에 존재하고있는지 확인하는 매처이다.

**JEST vs VITEST**

| 비교 항목      | `JEST`               | `VITEST`             |
| :------------- | :------------------- | :------------------- |
| **주요대상**   | 범용 JS 프로젝트     | Vite 기반 프로젝트   |
| **설정편의성** | 다소 복잡            | 매우 간편            |
| **속도**       | 보통(캐싱 의존)      | 매우 빠름(HMR 활용)  |
| **성숙도**     | 매우 높음(산업 표준) | 높음(빠르게 성장 중) |
| **ESM 지원**   | 까다로움             | 네이티브 지원        |

**it 함수 vs test 함수**

| 구분          | `it`                               | `test`                            |
| :------------ | :--------------------------------- | :-------------------------------- |
| **기능**      | test 함수의 별칭 (동일함)          | 테스트 케이스 정의 본체           |
| **스타일**    | BDD (행위 주도 개발)               | TDD (테스트 주도 개발)            |
| **권장 문구** | it('should ...') (~해야 한다)      | test('adds ...') (~를 테스트한다) |
| **가독성**    | describe 블록 내에서 문장으로 읽힘 | 단일 테스트 명세로 직관적임       |

**toBeInTheDocument() 매처를 사용하는 이유**

아래 예시와 같이 toBeInTheDocument() 매처를 사용하면 기존의 매처보다 코드가 직관적이고 가독성이 좋다.

| 방식            | 코드 예시                                               |      가독성      |
| :-------------- | :------------------------------------------------------ | :--------------: |
| **기본 매처**   | `expect(button !== null).toBe(true)`                    |     ❌ 낮음      |
| **기본 매처 2** | `expect(document.querySelector('.btn')).not.toBeNull()` |     ⚠️ 보통      |
| **jest-dom**    | `expect(button).toBeInTheDocument()`                    | ✅ **매우 높음** |

# 🍀 2.3. setup과 teardown

테스트 순서에 따라 결과가 바뀐다면 좋은 테스트라고 할 수 있을까? 당연히 아니다. 모든 테스트는 완전히 독립적으로 실행되어야 한다. 이러한 테스트의 독립성을 보장하기 위해 setup과 teardown을 활용할 수 있다.

**setup**: 테스트를 실행하기 전 수행해야 하는 작업(beforeEach,beforeAll)

**teardown**: 테스트를 실행한 뒤 수행해야 하는 작업(afterEach,afterAll) 

beforeEach와 beforeAll 이 동일한 스코프 내에서 실행된다면 beforeAll이 먼저 실행된다.

root-beforeEach, root-beforeAll, describe-beforeEach 이렇게 세개가 있으면

실행결과는 다음과 같다.

```
//실행결과
root-beforeAll
root-beforeEach
root-beforeEach
describe-beforeEach
```

 

setup과 teardown을 파일 하나가 아닌 앱에 존재하는 모든 테스트에 적용하고 싶다면?

->vite.config.ts파일에 작성해둔 setupFiles를 활용하여 전역으로 작성할 수 있다.

테스트 환경이 브라우저가 아닌 nodejs이기 때문에 어쩔수없이 전역에서 모킹이 필요할 때가 있는데 예를 들어 matchMedia가 jsdom환경에서 존재하지 않아서 테스트 실행 시 에러가 나는 경우가 있는데 이러한 경우 테스트 실행을 위해 사전에 matchMedia의 구현을 모킹해서 테스트 실행에 문제가 없도록 해야한다. 또한 확장하거나 매처를 추가하고 싶을 때도 setupTest.js 에서 작성해준다.

setup, teardown에서 전역변수를 사용한 조건 처리는 독립성을 보장하지 못하고, 신뢰성이 낮아지므로 지양하자

# 🍀 2.4. React Testing Library와 컴포넌트 테스트

[Testing Library 공식문서](https://testing-library.com/docs/)

Testing Library는 UI 컴포넌트를 사용자가 사용하는 방식으로 테스트한다.
사용자가 앱을 사용하는 방식과 테스트 방식이 유사할수록 신뢰성이 향상되기 때문이다.
이를 위해 Testing Library에서는 DOM과 이벤트 인터페이스를 기반으로 요소를 조회하고, 다양한 동작을 시뮬레이션 할 수 있다.
요소 조회를 위한 [쿼리](https://testing-library.com/docs/queries/about)는 다양하며 우선순위가 존재한다.

[spy 함수](https://vitest.dev/api/vi.html#vi-fn)는 함수의 호출 여부, 인자, 반환 값 등 함수 호출에 관련된 다양한 값을 저장한다.

언제 사용할까?
콜백 함수나 의존성 주입을 테스트할 때 사용한다.

# 🍀 3.1. 단위 테스트 대상 선정하기

- 커버리지 100% 를 위한 테스트는 의미없다.

- state나 로직 처리 없이 UI만 그리는 컴포넌트는 검증하지 않는다.
  해당 검증은 스토리북과 같은 도구를 통해 컴포넌트의 스타일이나 레이아웃이 틀어지지않는지 검증하는 것이 더 중요하다.

- 간단한 로직 처리만 하는 컴포넌트는 상위 컴포넌트의 통합 테스트에서 검증한다.

- 컴포넌트외에도 리액트 훅과 유틸함수를 단위테스트로 진행할 수 있다.
  공통 유틸 함수는 단위 테스트로 검증한다.
  다른 모듈과의 의존성이 없다.
  여러 곳에서 사용되기 때문에 검증을 통해 안정성을 높인다.

# 🍀 3.2. 모듈 모킹(Mocking)

EmptyNotice, NotFound, ErrorPage 컴포넌트를 살펴본다.

세가지 컴포넌트 모두 react-router에 의존성을 가지고 있고 useNavigate 훅을 가지고 있습니다.

그렇다면 useNavigate()을 검증해야할까? 이미 라이브러리 내부적으로 검증된 상태이기 때문에 useNavigate()에 대한 추가 검증은 불필요하고 제대로 호출되었는지만 검증하면 된다.

단위 테스트에서 외부 모듈에 대한 검증은 완전히 분리하고 모듈의 특정 기능을 제대로 호출하는지만 모킹을 이용해서 검증한다.

**모킹**이란? 실제 모듈·객체와 동일한 동작을 하도록 만든 모의 모듈·객체(Mock)로 실제를 대체하는 것을 말한다.

**모킹의 장단점**

👍 외부 모듈과 의존성을 제외한 필요한 부분만 검증이 가능하다.

👎 실제 모듈과 완전히 동일한 모의 객체를 구현하는 것은 큰 비용이 든다.

👎 모의 객체를 남용하는 것은 테스트 코드의 신뢰성을 낮춘다.

vitest에서는 vi.mock()을 사용하여 모킹할 수 있다.

**모킹 초기화**

각 테스트의 독립성과 안정성을 보장하기 위해 teardown에서 모킹을 초기화하자

vitest의 [resetAllMocks](https://vitest.dev/api/vi.html#vi-resetallmocks), [clearAllMocks](https://vitest.dev/api/vi.html#vi-clearallmocks), [restoreAllMocks](https://vitest.dev/api/vi.html#vi-restoreallmocks)를 활용해 초기화하자
